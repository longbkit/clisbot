# Storage benchmark (frozen source) — 2026-09-12

This is a completed **frozen-source** benchmark run: the full dataset set finished,
every phase exited cleanly, and the process reported `exit=0` across 28 phases with
no failed phase. Unlike the [2026-09-11 diagnostic](2026-09-11-diagnostic.md) (whose
source tree changed mid-run), the measured production source here is byte-stable for
the whole run. The README p95 targets it is compared against are still **unmeasured
targets** on production web/desktop; what is measured here is the daemon
store/read/write boundary on this machine, stated plainly below.

The complete, unedited [JSON artifact](2026-09-12-frozen.json) includes per-phase
measurements, exact source fingerprints at start and end, machine/mount data, the
fixed storage limits, and workload parameters. The [harness

Companion probes on the same source:
[derived-allocation](2026-09-12-derived-allocation-frozen.json) (derived-node counts +

The large dataset mixes running/completed tools, reasoning and assistant chunks,
logical user-message IDs/senders, and attachment references. Baseline eager
projection retains/copies the full in-memory rows and does not acknowledge durable
writes or include provider history loading. These are architectural components, not
equivalent end-to-end paths.

Seeding 100,000 canonical rows in batches of up to 256 took 520.51 s: 192.12
records/s, 51.6 KiB/s, batch acknowledgement p95 2,317.8 ms. The canonical fixture
contains 27,526,783 logical bytes. Node instrumentation observed 37,438 fsyncs
(sync mean 5.94 ms, max 418.80 ms); Linux `/proc/self/io` reported 155.4 MiB
physical write bytes.

Ten concurrent writers each awaited 1,000 single-row durable calls: all 10,000 rows
completed and verified in 676.66 s, 14.78 records/s, 3.8 KiB/s. Durable
acknowledgement p50/p95/max was 567.4 / 1,314.7 / 5,165.6 ms. There were 193,371
fsync calls and 563.4 MiB of Linux physical write bytes for 2,665,180 logical row
bytes. Event-loop lag p95/max was 18.78 / 307.23 ms; peak heap/RSS 74.6 / 244.6 MiB.
This single-row write amplification (193,371 fsyncs for 10,000 rows) is retained as a
finding, not hidden by bulk throughput. This phase ran interference-free (no
competing process), so it is the cleaner of the two writer runs — it is 2.0× slower
than the diagnostic's 339.66 s, which ran on a less loaded machine; the difference is
machine load, not source.

Six cycles visited 160 distinct one-row sessions using a 128-owner FileStore budget.
Every cycle retained exactly 128 owners. Post-GC heap per cycle: 55.7 / 55.6 / 55.5 /
56.9 / 57.1 / 56.9 MiB; post-GC RSS held 244.6–244.7 MiB. The predefined plateau
criterion passed (`heapPlateauObserved: true`, `allowedGrowthBytes` 11,269,744). This
demonstrates only this FileStore ownership workload: no claim about global
daemon/client/provider, attachment/fork, subagent, subscription or rendered view
retention follows from it.

## Whole-daemon steady-state (AC6)

A separate loop
(`whole-daemon-steady-state.ts`) boots a real in-process daemon, seeds 200 sessions ×
204 rows through the daemon's shared 128-owner store, then runs 6 cycles of open
projected tail + one scroll page + directory lookup per session through the daemon's
real `agentManager.fetchProjectedTimelineForRead`, sampling post-GC RSS/heap, the
resident owner count, event-loop lag and `/proc/self/io` per cycle. Results:

- 6 cycles, 128/128 resident owners each (`ownersBounded: true`);
- post-GC RSS 336.1 → 336.6 MiB across cycles, **0.5 MiB growth first→last** (steady
  state reached);
- post-GC heap ~158.0–158.1 MiB, flat;
- event-loop lag p95 16.9 → 16.1 ms (no growth);
- restart proof: a fresh daemon over the same home lists all 200 sessions and reads
  the last session's tail to `endSeq=204` while the agents are closed.

The whole-daemon RSS (~336 MiB post-GC) is above the FileStore-only plateau (~245
MiB) because it includes the agent storage registry, manager, and server scaffolding.
The queue does not grow at this fixed sequential load: the store caps pending journal
bytes at 16 MiB and 1,024 queued operations and rejects beyond that (verified by
`pending-event-budget` tests).

## README p95 targets — plain statement

The README states initial web/desktop production targets (daemon ready, SSD, local
network): p95 click→last-page ≤ 1 s with empty cache / valid index; ≤ 200 ms with
cache; scroll page ≤ 300 ms. These are explicitly **unmeasured targets**, not current
numbers, and were not measured here (no app, wire, provider, or packaged daemon). At
the **daemon store/read boundary** on this container, the measured p95s are:

- Cold valid-index tail: **340.5 ms (100k) / 551.6 ms (1k)** — within the ≤ 1 s target.
- Cached (warm-owner) tail: **353.1 ms (100k) / 746.2 ms (1k)** — **does not meet** the
  ≤ 200 ms target at the storage boundary on this machine.
- Scroll (older page): **184.4 ms (100k) / 141.2 ms (1k)** — within the ≤ 300 ms target.

The ≤ 200 ms cached target is unmet at the storage boundary here; the ≤ 1 s cold and
≤ 300 ms scroll targets are met. Production end-to-end click latency (app→wire→daemon)
remains unmeasured and is out of this lane.

## Instrumentation limits and remaining acceptance work

Node read instrumentation counts `readFile` and explicit `FileHandle.read`, not
internal `createReadStream` reads; `/proc/self/io` supplies process-wide
logical/physical counters. Filesystem page-cache hits naturally have zero physical
read bytes. Event-loop histograms may have no samples during an entirely synchronous
baseline phase; zero/NaN means unobserved, not zero blocking. RSS peaks can retain
allocator pages from earlier baseline phases; inspect start/end/post-GC values in JSON
before attributing a peak to one store operation.

Fixed store limits during the run: 16 MiB pending journal bytes, 1 MiB batch, four
concurrent journal I/O operations, 8 MiB segment/read-page limits, 256-row index
pages, 128 FileStore owners, 1,024 queued FileStore calls, and projection budgets of
16 MiB per operation / 32 MiB global. The ten writers had one outstanding call each,
so this workload does not test overload rejection. These budgets do not account for
every upstream daemon/client queue.

Still required beyond this lane: production web/desktop packaged-daemon timing for the
README p95 targets (especially the ≤ 200 ms cached target, unmet at the storage
boundary); full daemon/provider and production-browser timing; Android/desktop
retention evidence; power-loss/Windows distinction (crash evidence here is
process-kill only); and the real upstream merge rehearsal plus an independently pinned
compatibility matrix. No AC is marked complete by this checkpoint alone.
