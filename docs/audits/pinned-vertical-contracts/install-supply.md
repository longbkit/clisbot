# Install + supply

Verified against the registry bytes (integrity-matched) on 2026-08-26, not against a
pre-provisioned checkout:

- The `@openclaw/slack` tarball ships a complete `node_modules` (5274 entries: `@slack/bolt` 4.7.3, `@slack/web-api` 7.18.0, `axios`, `ws`, `zod`, `typebox`, …). Self-contained.
- The main `openclaw` tarball ships **no** `node_modules` at all. It ships declared `dependencies` (~60 packages) plus a fully-resolved `npm-shrinkwrap.json` (308 lockfile packages, each with `resolved` URL + `sha512` integrity). Any earlier note claiming the main tarball ships its own `node_modules` (e.g. "581 top-level packages") read a provisioned checkout and is wrong; a registry download of the pinned version has zero `node_modules` entries.

Because the main dist chunks bare-import their deps (e.g. `typebox` from `dist/schema-validator-*.js`) and both channel entries load main-dist chunks, the main dir needs its dependency tree or nothing loads. `npm ci` in the extracted main dir crashes arborist on this lockfile's peer-set shape (`Cannot read properties of null (reading 'edgesOut')`, npm 10.9.8; reproduced with `ci`, `install`, and `--omit=dev`), so the install plane provisions the tree itself: `packages/hub/src/channels/install/provision-main.ts` reads the shrinkwrap out of the extracted main dir, computes the production closure (root `dependencies` + `optionalDependencies`, nested-then-ancestor resolution; 303 entries for the current pin), fetches each entry through the injectable `fetch` seam, verifies the bytes against the lockfile-recorded integrity **before** extraction, and extracts into `mainDir/node_modules/…`. The managed root `CLISBOT_HOME/plugins/channels/package-lock.json` records package metadata; no custom provision marker is created. No build scripts run; module resolution is all the loader needs.

Trust boundary: the shrinkwalk is inside the integrity-pinned main tarball, so its `resolved` URLs and integrity records are inside the pin's trust boundary — provisioning fetches exactly what the pin says. Idempotence is the tree's own completeness: re-runs are a no-op while every production-closure package is extracted, and a deleted tree self-heals on the next install. `ensureChannelInstalled` calls this only when the extracted main dir contains an `npm-shrinkwrap.json`, so a main tarball that ships its own `node_modules` (the Slack shape) is left alone.
