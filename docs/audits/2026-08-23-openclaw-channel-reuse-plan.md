# PaseoClaw Fusion — Channel Capability: Problem Map, Foundation, and Reuse Plan

Date: 2026-08-24, final decisions 2026-08-25. Subject: the full channel capability for the fusion — same-machine channels, native per-channel formatting, and how it relates to the existing Paseo Hub trigger layer — built on OpenClaw's published channel code. Registry and package claims were verified against the public npm registry and published tarballs on 2026-08-23/24; code claims in this repo carry paths; Hub claims come from [2026-08-23-paseo-hub.md](2026-08-23-paseo-hub.md).

**Headline (decisions §14.6/§14.7, 2026-08-24/25).** The channel control plane lives in the **Hub** (§4-S2); the Hub reaches the daemon as an **ordinary client** in both deployment forms — embedded pairs over loopback, team/remote pairs over the relay like any Paseo client (a relay-attached socket is `scopes: ["*"]`, `kind: "trusted"` — `websocket-server.ts:1342/1391`; only `attachHubSocket` is scope-narrowed). Channel code (OpenClaw's published channels) runs **in-process in the Hub** (§14.5). The daemon's P0 channel diff is **zero**: steer + approval ride the existing trusted-client RPCs, and the per-session/per-resource grant engine — which narrows any bound-principal session — moves to **P1** and applies to all clients. The upstream scoped channel (`hub.execution.*`) is **frozen legacy-compat, expected to sunset**: no form rides it by design at P0.

**Status (2026-08-26): the supply model changed for Slack and Telegram.** Both P0 verticals are now **first-party in-repo packages** (`packages/channels/slack`, `packages/channels/telegram`, shared `packages/channels/shared`) — OpenClaw's code ported in-repo, zero `openclaw/*` imports, driven through the same drive surface (`plugin.gateway.startAccount` + `plugin.outbound.sendText`). The pinned OpenClaw dists stay in `channel-pins.json` as **upstream sync references only** (`loadMode: "in-repo"`, no tarball fetch, no integrity gate). The pull, its scope, and the re-sync loop: [2026-08-26-in-repo-channel-verticals.md](2026-08-26-in-repo-channel-verticals.md) — read its §1 (the contract that survives) and §6.5 (the executed blueprint) before touching the channel plane. This plan's §4-S1 option B (published tarball + alias seam) remains the supply model for **pinned** channels (zalouser and later); it is no longer how Slack or Telegram reach the Hub.

## 1. Scope

This plan owns the channel capability end-to-end: what problems it solves, what existing foundations it builds on, which solutions were chosen and why, and how to add channels over time. The workspace-init template it depends on is planned in [2026-08-23-paseoclaw-fusion-gaps.md](2026-08-23-paseoclaw-fusion-gaps.md); the T3Claw reference is audited in [2026-08-23-clisbot-t3claw-fusion.md](2026-08-23-clisbot-t3claw-fusion.md); the build/publish/onboarding/source-change implementation is at [2026-08-24-hub-integration-implementation.md](2026-08-24-hub-integration-implementation.md).

## 3. Existing foundations

What this plan builds on instead of rebuilding.

### A. Paseo Hub — the channel control plane (already exists; extended, not replaced)

The ownership call behind this section (restated in §4-S2): the channel control plane lives in the Hub, not in a new daemon module — the earlier draft's channel host is dissolved into it. The Hub already owns most of what a control plane needs; concretely available today (all in `getpaseo/hub`):

- **Trigger providers already implemented**: `slack.mention` (Socket Mode + webhook), `github.*` (signed webhooks), `discord.mention` (gateway), `manual.run`. Full event surface and the two-output (`slack.reply`, `discord.reply`) capability set: Hub audit "Output and event surface" (re-verified 2026-08-24).
- **A durable, revisioned configuration model** — the natural home for channel config: `.paseo/hub.yml` (environments + agents) plus one trigger per `.paseo/workflows/*.yml`, compiled into an immutable active revision (`src/config/compiler.ts`, `bundle.ts`), with prompt partials/includes, per-step agent selection, and output schemas. Channel accounts/routes/policies plug in as a new authored block on this same compiler (§4-S2).
- **A durable dispatch + workflow engine** with idempotent dispatch (`executionId`), auto-archive, and a per-execution MCP endpoint (`finish_execution`, structured outputs) — the mechanism channel-originated turns ride as a generalized entrypoint, not a new invoke API (§4-S2 gap 11, §9 step 4).
- **Org-level connections** (`slack_connections`, `discord_connections`, `github_connections`) with unique-per-instance indexes, plus metering/entitlements.
- **An embedded runtime**: with `DATABASE_URL` unset the Hub runs a PGlite file DB (`src/db/runtime/internal/embedded.ts`, data dir via `PASEO_HUB_DATA_DIR`, defaulting to `$XDG_DATA_HOME/paseo-hub`), so a same-machine Hub needs no separately deployed Postgres; the Postgres path (`DATABASE_URL` set) is the team form. \_(Fork override, §14.8: operators set `CLISBOT\__`names and the default home is the shared`~/.clisbot`; the `CLISBOT*\*`→`PASEO*_` alias keeps the upstream names internal.)\_
- **The agent stream already reaches it**: `agent_stream` events (timeline + `permission_requested`/`permission_resolved`) arrive over the trusted session the Hub pairs on — the same per-agent subscription the app uses. That is the relay and approval input for both forms at P0 (§14.7); the scoped `hub.execution.agent.stream` consumer is kept only as the frozen legacy-compat path. No new daemon→Hub transport is needed.
- **Public ingress routes + a manual dispatch path already exist**: per-provider named-request routes (`/webhook` for the GitHub signed webhook, `src/routes/webhook.ts` → `requests.get("webhook")`; `/api/integrations/slack/events` via `handleProviderRequest("slack.events")`, request names per provider at `src/provider-applications/internal/runtime-owner.ts:395`), OAuth callbacks, the billing webhook, a **manual trigger dispatch public operation** with named entrypoints (`public-operations/`, `source: "manual.run"`, `handleManualTriggerRequest` at `src/triggers/manual/source.ts:32`, entrypoint routes at `src/routes/test/trigger.ts` / `smoke.ts`), and a per-execution MCP endpoint (`src/routes/agent-executions/$executionId/mcp.ts`).

What Hub lacks is the problem list P3–P6 (no thread→session continuity, no policy-filtered outbound, no approval forwarding, allowlist-only auth) — the extensions this plan adds **to the Hub** (§4-S2). Because the extension is Hub-side, the daemon's P0 diff is zero (§4-S3, §14.7); the P1 grant engine is the only later daemon addition.

### B. Paseo daemon — agent owner, kept upstream-pure (verified)

The daemon owns agent sessions, timelines, permissions, and workspaces, and already exposes exactly the seams a control plane needs. Its P0 channel diff is **zero** — both Hub forms drive agents through the stock trusted-client RPCs (§14.7); the only later addition is the **P1 per-resource grant engine** (dedicated module, flag-gated, §4-S3). Verified seam set (all `@getpaseo/server` internal):

- **Timeline live**: `agentManager.subscribe(callback, { agentId })` → `AgentManagerEvent`, whose `agent_stream` variant carries an `AgentStreamEvent` incl. `turn_started/completed`, timeline items, `permission_requested/resolved`, `attention_required` (`packages/server/src/server/agent/agent-manager.ts`, `packages/protocol/src/agent-types.ts`). P0 relay input (both forms, §14.7): the Hub's trusted session subscribes to the bound `agentId` through the app's per-agent subscription (`selectiveAgentTimeline` + `agent.timeline.set_subscription`). The scoped path's ownership-filtered `hub.execution.agent.stream` forwarder (`packages/server/src/server/hub/daemon-executions.ts`) is kept only as the frozen legacy-compat path.
- **Inbound prompt**: `sendPromptToAgent` / `startAgentRun` with `activeTurnBehavior: "steer"` — the doc-commented single path every surface must use (`packages/server/src/server/agent/agent-prompt.ts`). This is the exact primitive thread continuity rides on (trusted `send_agent_message_request` → this); no new prompt path is needed.
- **Agent lifecycle + approval**: `createAgentCommand` (the entry both the trusted client and the scoped Hub use), `archiveAgentCommand`, `respondToAgentPermission` (`packages/server/src/server/agent/permission-response.ts`). The trusted `create_agent_request` and `agent_permission_response` RPCs call these same primitives — the seam set is shared, not forked.
- **Scoped execution contract (upstream, frozen legacy-compat)**: `DaemonExecutions implements HubExecutionAgents` (`packages/server/src/server/hub/daemon-executions.ts`) — the WS RPC handler for the `hub.execution.*` channel. Untouched by the fork; no form is designed to use it at P0; expected to sunset with the P1 grant engine (§14.7).
- **Managed processes (P1 option only)**: an existing file-backed registry (`packages/server/src/server/managed-processes/`, `createManagedProcessRegistry`) records daemon-spawned helper child processes and reaps orphans at startup. It does not spawn or restart; a daemon-managed embedded Hub (spawn + backoff + crash-loop breaker on this registry) is a **P1** option, off-by-default. P0's embedded Hub is operator-supervised.
- **Transparency**: the client sees channel-originated sessions as ordinary agent sessions — timelines, side panel, worktrees, approvals. The advantage over OpenClaw and Hermes, where the chat surface _is_ the only surface.

### D. T3Claw Fusion — validated design patterns (reference, not code)

From [2026-08-23-clisbot-t3claw-fusion.md](2026-08-23-clisbot-t3claw-fusion.md): coordinator as the only component that starts a session; one stateless policy service; thread bindings with `initiator` recorded once; **host-driven timeline relay** (the host, not the agent, decides what the channel sees — per-kind sync flags over the same thread stream the web client rides, progress/tool events throttled and deduped through a delivery ledger that records before it posts) — the flexible outbound mechanism this plan keeps, in contrast to Hub's agent-invoked `reply` tool (§2 P5); first-match-wins approval rules with `require` decisions, privilege-wildcard approvers, and inert wrong approvers (§4-S6); channel-originated turns in `approval-required` mode; two independent authority checks (inbound entry + approval exit); surface-matrix discipline; a hard gate on adding a channel (§9). Its audit script, despite being documented as a CI gate, is **not invoked by any workflow in that repo's `.github/workflows/`** (verified 2026-08-24: `audit:origin`/`sync:origin` exist as package scripts, no workflow calls them) — ours is a CI step from day one.

Decisions on B's cons (each is a plan item):

- **Registry dependency**: pin the public supply directly — published npm tarballs by `dist.integrity`, no private mirror (§14.4 decision); the public git repo at the pinned `gitHead` is the fallback supply mode behind the identical seam interface, so A is an escape hatch, not a re-architecture.

- **Version drift**: one pin manifest (`channel-pins.json`) pins main + all channels; CI runs the import conformance check (generalized 331/0 probe) plus the `compat.pluginApi` floor.
- **Transitive agent-loop loading**: the matrix classifies by the static import graph of the dist, not by name; the load-trace check at load (§6) is the load-time proof.

### S2. Channel control plane in the Hub (P1, P3, P4, P5, P6, P8, P9, P12, P13)

The decisive ownership call, restated from §3-A: **the channel capability's brain lives in the Hub** — the earlier draft's `PaseoChannelHost` (daemon module) is dissolved into it. The Hub owns channel **configuration**, **authorization**, **thread bindings**, the **outbound relay policy**, **approval rules**, and, since the §14.5 decision, the channel **verticals** themselves (OpenClaw's published code, in-process, per channel, §4-S1). No one outside the Hub owns channel policy, and no channel code runs anywhere but the Hub; the daemon stays agent owner with zero P0 channel diff (§4-S3).

**Ownership table.**

| ------------------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Channel config (accounts, routes, roles, sync, approval rules)      | Hub config bundle                                 | New authored block on the existing compiler (§3-A); one revision = one snapshot; live reload = new revision                                                                                                        |
| Thread → session binding                                            | Hub DB                                            | Durable record, survives Hub and daemon restarts (Postgres team form; PGlite embedded form)                                                                                                                        |

| Channel transport, native rendering, chunking, media                | Channel vertical (Hub module, in-process — §14.5) | Slack/Telegram: first-party in-repo packages (`packages/channels/*`, 2026-08-26 pull); zalouser + later: OpenClaw published code, integrity-pinned, installed per channel; loaded into the **Hub**, not the daemon |
| Agent sessions, timelines, permissions, workspaces                  | Daemon                                            | Unchanged at P0 (zero diff); the P1 grant engine is the only later daemon addition (§4-S3)                                                                                                                         |

**What changes in the Hub, part by part.**

- **Configuration model.** The existing bundle (`.paseo/hub.yml` environments + agents, one trigger per `workflows/*.yml`, compiled to an immutable revision — `src/config/compiler.ts`, `bundle.ts`) gains an authored **directory**: `.paseo/channels/` with `policy.yml` (org-scope `roles` + `users` + `assignments` + defaults, S4 privilege algebra) and one file per bot account, `channels/<channel>/<accountId>.yml` (identity: `enabled` + `secretRef`; `transport` channel-native block; `policy` = account `defaultRoles` + `assignments`; `defaults` = `interaction`/`binding`/`reply`/`sync` per S5 / `approval` rules per S6; `routes[]` ordered first-match, each `match`ing a conversation kind/ids and targeting a continuous session (`agent` + `environment` references into `hub.yml`) or a workflow, with per-route overrides of the same keys + route-scope `assignments`; `fallback`). **Revision 2026-08-25 (supersedes the original "channels: block in hub.yml" wording):** the upstream compiler rejects unknown top-level keys in `hub.yml` (`rejectResourceKeys`, `bundle.ts:238`) and enforces one trigger per `workflows/<name>.yml` file, so a new top-level `channels:` key would not compile at all; a dedicated directory mirrors that enforced file-per-resource pattern, keeps `hub.yml`/`workflows/` byte-identical (P10 mergeability), and matches the per-account runtime layout (install dir, transport, ingress route). Chat routes do not carry trigger blocks: a thread runs a continuous session (create + steer, this plan's execution model) or hands off to an existing `workflows/<name>.yml`. `defaultAccess` was also replaced by role lists (`defaultRoles`: `[]` = deny-by-default, `[user]` = all mapped members may trigger) — "who may trigger" is the existing `bot.interact` privilege, not a new enum. Full file shapes and the per-file enum tables: [2026-08-24-hub-integration-implementation.md](2026-08-24-hub-integration-implementation.md) §4.3. Compilation reuses the existing validation/revision machinery, so channel config gets Hub's durability, audit hash, and "active revision" semantics for free. Secrets stay out of the bundle via `secretRef` (0600 file, Hub-owned). The `from_users` allowlist of today becomes a degenerate route policy: a route whose policy grants `bot.interact` to all members expresses "all users may trigger", which the current compile-enforced allowlist cannot.
- **Connections.** Today one Slack team / Discord guild / GitHub installation per Hub instance (globally unique indexes, `src/db/schema.ts`) — P4. Channel accounts need **many accounts per provider per org** (two Slack workspaces, a second Discord guild). Model: account-level records under the existing org connections (e.g. `slack_accounts` keyed by `(org, team, app)`), with the connection holding credentials and the account holding per-workspace settings. The trigger providers already resolve `botUserIdForWorkspace`/tokens per org+team (`src/providers/slack/index.ts`) — the account dimension is a generalization, not a new mechanism.
- **Execution model: continuous executions.** Hub executions today are event-scoped: one `executionId`, fresh workspace, no thread key (`src/workflows/engine.ts`). Channel threads need the other shape: first message in an unbound thread → `create` (trusted `create_agent_request`) + record a **thread binding** (external thread key ↔ `agentId`, `initiator` principal, route, recorded once, plus a pre-create pending marker for orphan recovery); every follow-up in the bound thread → **resume/steer the existing session** (`send_agent_message_request` with `activeTurnBehavior: "steer"` — the same semantics the daemon's `sendPromptToAgent` already implements). The binding is a durable Hub record, so a follow-up after restart resumes the same session — P3, closed. Because the trusted path has no create-dedup, the binding record **is** the idempotency (see "Same-machine deployment" below). The **granularity** of the binding key is route/account config — `binding.key: thread | channel | dm` (default `thread`: each native thread/topic gets its own session; `channel`: the whole conversation is one session, all threads collapse into it; matches OpenClaw's per-topic session keys and T3Claw's per-thread `thread_binding`) — and outbound posting location is independent (`reply.anchor: default | thread`), so "one session per whole channel, replies follow the marker's level" and "one session per topic, replies in the topic" are both one-line configs (implementation doc §4.3.4).
- **Outbound path.** The relay (S5) is a Hub consumer of the agent timeline — the P0 relay input, both forms (§14.7): the Hub's trusted session receives the ordinary client `agent_stream` events for its bound `agentId` (the app's per-agent subscription; the scoped `hub.execution.agent.stream` is the frozen legacy-compat consumer, not a P0 relay input). The relay mapper + delivery ledger (record-before-post, dedupe on replay — T3Claw's `RelayEvent`/ledger semantics) run in the Hub; delivery calls the channel's send path (its published `message`/`outbound` adapters, in-process — §14.5), so native chunking/rendering still runs. The agent-invoked `slack.reply`/`discord.reply` output tools stay available alongside: two outbound paths (the Hub relay + the agent-driven reply tool), and route policy sets which is the default — for real-time channel use the relay is primary, the `reply` tool remains for multi-step workflows that compose outputs explicitly.
- **Approval path.** `permission_requested` arrives on the same stream (§14.7). The Hub classifies it against the route's approval rules (S6), auto-responds `allow`/`deny` cases, and for `require` posts a prompt to the bound thread (text + command in P0, native card in P0.5 — **2026-08-27: the native card is pulled into P0 for the in-repo Slack/Telegram verticals, see the dated decision in §4-S6**). The responder's answer is re-authorized (S4) and dispatched via the **existing trusted-client `agent_permission_response` RPC** (the same one the app UI answers with) — no new wire. The P1 grant engine narrows the full-trust session it dispatches from; the scoped channel (which has no permission-respond RPC at all) is not on this path.
- **Gaps the Hub must fill (the full list).** P0 closes the two former wire gaps (thread resume/steer, permission-respond) with the **existing trusted-client RPCs** — no new wire. The Hub-side gaps: (3) multi-account-per-provider connections; (4) continuous execution + thread-binding persistence; (5) outbound relay + delivery ledger; (6) channel config directory + account-level secrets; (7) approval rules + prompts (S6); (8) RBAC over org principals replacing allowlist-only auth (S4); (9) DM/slash/interactive surfaces per channel (P1+); (10) channel vertical lifecycle in-process (per-channel load gate + load-trace check at load, §6/§14.5 — the draft's child-process supervisor is replaced by the in-process decision); (11) channel ingress routes — a generalization of the Hub's existing per-provider named-request ingress to per-account channel routes: the route hands the raw payload to the owning vertical, where the channel's own signing checks run before the typed event is dispatched in-process (P13 is now "third-party code runs only in its own pinned install under its own tokens", §14.5); channel-originated turns ride the same trigger-run dispatch the `manual.run` public operation already exposes — a generalized entrypoint, not a new invoke API (P0.5, §9); (12) user-identity mapping + pairing-link minting over the enrolled `daemons` rows (§4-S4; the resource-grant enforcement is the P1 daemon grant engine, §4-S3). All of 3–12 are Hub-side modules with no P0 daemon impact.

**Same-machine deployment: the embedded Hub is a trusted client.** The one-person setup runs an **embedded Hub** — PGlite file DB, no `DATABASE_URL` (operator: `CLISBOT_HUB_DATABASE_URL` unset), data dir via `PASEO_HUB_DATA_DIR` (operator: `CLISBOT_HUB_DATA_DIR`, default the shared home `~/.clisbot`, §14.8) — next to the daemon. It reaches the daemon the same way §4-S3 describes for both forms: loopback WS, `hello`, attach with `scopes: ["*"]`. The trusted path does not give two things for free; both are owned Hub-side (no daemon change):

- **Idempotency.** The scoped path deduped creates on `executionId` (`daemon-executions.ts` `findByDaemonExecution`); the trusted `create_agent_request` does not — a redelivered create spawns a second agent. The Hub owns a durable **executionId ↔ agentId ledger** (its thread-binding record) plus a _pre-create pending marker_, and on restart does **orphan recovery**: a trusted session sees all agents, so it scans `fetch_agents` for unbound agents matching its own marker and rebinds instead of re-creating. Orphans are visible in any paired app (transparency), which bounds the damage. The create-then-crash window is the one residual race (P0 acceptance case, §10).
- **Security posture of the team/remote form (what bounds the full-trust pairing).** At P0 the team/remote Hub is a _single_ full-trust principal (the Hub itself) on the daemon; the per-user RBAC lives in the **Hub** (§4-S4), not the daemon. A malicious Slack message is stopped by the agent-layer backstop — `approval-required` (S10) + the provider permission system (native tools not pre-approvable via `toolPolicy`) + S6's two authority checks — not by the wire. The P1 **daemon grant engine** is what narrows the full-trust session (steer + permission-respond for a bound Hub principal become grant-gated, and cross-session / config / `daemon.update` reach is closed). Until it lands, the team form's defense-in-depth is pairing + the agent layer + the Hub's own RBAC; the scoped channel is retired rather than extended because it was never the boundary that stopped a malicious message.

The daemon never learns _why_ a call arrived — a trusted RPC from either Hub form is indistinguishable from one from the app, which is exactly the "Hub stays the control plane in every deployment" property, achieved without a dedicated seam.

**What the channel vertical is, now.** A **Hub module, in-process** (§14.5 decision): the Hub loads the published OpenClaw channel code per channel — separate install dir, integrity-pinned, own tokens, load-trace-checked at load (§6) — and runs its adapters as first-class Hub code paths: inbound event → the channel's own signing checks + normalization → typed event to the trigger-run dispatch; outbound text/approval-card → the channel's send path; transport lifecycle (Socket Mode / polling / webhook) managed per channel. No vertical IPC surface, no vertical supervisor: the seam table (§7) binds subpaths directly to Hub modules. Blast radius is the accepted cost (P13, §14.5): a channel fault takes down the Hub with it, so the daemon — which owns every agent session on the machine — is the one process a channel can never reach, and the Hub needs an **external supervisor** (condition 2 of §14.5): at P0 the operator's own (systemd / `pm2` / the `clisbot` launcher); the daemon-managed form is a P1 option (§4-S3).

### S3. Daemon-side diff: P0 zero, P1 grant engine (P1, P10, P15)

**P0 — zero daemon diff.** Every form of the Hub reaches the daemon the same way the local CLI and web UI already do: open a WebSocket (loopback for the embedded form, relay-paired for the team/remote form — decision §14.7), complete the `hello` handshake (`packages/protocol/src/messages.ts` `WSHelloMessageSchema`), and attach as a **trusted session** with `scopes: ["*"]` (`websocket-server.ts` `attachSocket` → `createSessionConnection`; the relay path is `attachExternalSocket` → `attachSocket`, same `createSessionConnection`). No enrollment, no credential, no new RPC, no capability flag, no new handshake message. Every channel primitive it needs is an **existing trusted-client RPC**, verified present on the wire:

- **Create** — `create_agent_request` → `createAgentCommand`, with `config.mcpServers` + `config.toolPolicy` accepted exactly as the scoped path injects them (the Hub-injected per-execution MCP endpoint + completion token ride the config the same way).
- **Thread continuity** — `send_agent_message_request` with `activeTurnBehavior: "steer"` (the doc-commented single prompt path, `packages/server/src/server/agent/agent-prompt.ts`), targeted at the bound `agentId`.
- **Approval exit** — `agent_permission_response` (the same RPC the app UI uses to answer a pending permission), shape `allow` (`updatedInput` / `updatedPermissions`) / `deny` (`message` / `interrupt`), wrapping the existing `respondToAgentPermission`.

Consequences of P0 zero:

- **Upstream mergeability (P10) is structural and cheaper than before.** The monorepo diff for the channel feature is `packages/hub` (new directory) + the additive `clisbot` CLI groups (implementation doc §1.4/§3.2): no new daemon RPC, no new wire schema, no `server_info.features` flag, no `COMPAT` tag. The unmodified Paseo app pairs to the fork daemon byte-identically to upstream and sees channel-originated agents as ordinary agent sessions.
- **One authorization authority is still the Hub** (channel-side, §4-S4). The transparency property is unchanged: clients render channel sessions natively because they talk to the daemon.

**Both forms pair as ordinary clients at P0 (decision §14.7)** — embedded over loopback (loopback reachability = operator, `SECURITY.md`), team/remote over the relay like a phone, so both have steer + approval at P0. Full-trust is sound for the embedded form (same trust domain as the daemon); for the team/remote form it is _accepted at P0 and bounded by the P1 grant engine_, which narrows a bound-principal session regardless of form. The upstream scoped channel is frozen legacy-compat and expected to sunset (§14.7); no form rides it by design at P0.

**P1 — per-session/per-resource grant engine (the daemon's only channel-related addition).** A dedicated module (a `packages/server/src/server/grants/`-style scope, small additive hunks at the existing hook sites) that binds a **principal** to a session and enforces **resource grants** over the daemon's own hierarchy — which daemons, which projects, which agent sessions, which surfaces (terminals, files, …) — on **all** clients, including a full-trust Hub:

- Narrows a session only when a principal + grants are actually bound (additive optional handshake message, capability-gated on `server_info.features`, per `docs/protocol-compatibility.md`); a session with no bound principal keeps today's trust semantics, so ungranted/old sessions are never semantically narrowed.
- Is what makes the team/remote form's full-trust pairing _safe at scale_: narrowing a bound-principal Hub to its grants (closing the residual blast radius — pairing-offer exfiltration, cross-session reach, config mutation, `daemon.update`). It narrows a Hub exactly as it narrows any other client; the scoped channel is retired rather than extended (§14.6).
- Off-by-default and flag-gated; flag-off is byte-equivalent to upstream (verified per CLAUDE.md "verify both states").
- Stays **promotable** under the §14.1/§14.3 discipline (self-contained module, additive hunks, tests that pass unchanged against `main`).

The P0→P1 split is deliberate: P0 keeps the daemon pristine so the fork is cheap to maintain _now_; P1 carries the one genuinely cross-cutting upstream surface (a per-resource grant engine threads a session principal through `agentManager`, the workspace registry, the terminal manager, the file service, the config store, and checkout — the 157-case RPC dispatch). The distinction that keeps P1 from ballooning: P0's Hub-side RBAC (§4-S4) defends against **channel users**; the P1 daemon engine defends against a **compromised or buggy Hub process**. Only the latter needs daemon-side enforcement.

**Supervision.** With P0 zero, the embedded Hub is its own operator-run process — §14.5 condition 2, operator-provided (systemd, `pm2`, the `clisbot` launcher). The daemon-managed form (spawn + backoff + crash-loop breaker on the managed-processes registry, §3-B) is a P1 option, off-by-default, independent of the grant engine.

#### Obsolete — scoped-transport approach (superseded §14.6, 2026-08-24)

The earlier plan reached the daemon through an **enrolled scoped channel** — `attachHubSocket` + `hub.execution.*`, with a two-sided fork diff:

1. **Two additive RPCs** on `hub.execution.*`: `hub.execution.agent.steer.request` (thread continuity) and `hub.execution.agent.permission.respond.request` (approval exit), both thin forwarders to `sendPromptToAgent` / `respondToAgentPermission` with ownership checks.
2. **The scoped session** itself (enrollment credential, `hub.execution.*` grant, `isOwned` outbound filter) as the Hub's transport to the daemon.
3. **A grant-aware pairing handshake** (capability-gated) so the daemon knew _who_ a paired principal was and what it could do.
4. **Transport options A/B/C** (loopback-WS enrollment / in-process RPC / direct-connection adapter) plus a one-`HubExecutionTransport` seam.

Why it was set aside is recorded in decision §14.6 (three points: daemon-diff cost for a namespace that is not the security boundary; the trusted path already provides create + steer + permission-respond with zero daemon change; the grant model is cleaner as one P1 engine narrowing every session). The scoped **channel still exists upstream** — frozen legacy-compat as of §14.7, kept only for existing enrolled daemons and expected to sunset. No code in this fork implements items 1–4 at P0, and no form is designed to ride the scoped channel at P0.

### S4. Authorization: one policy service in the Hub, over org principals (P8, P6)

The policy service lives in the Hub, because the control plane lives in the Hub (§4-S2) — no second policy service exists anywhere else. It is built directly on T3Claw's validated privilege algebra so S6's rules have something to require: roles as named privilege sets (no rank), `extends` composition, `*` / `family.*` wildcards, `!priv` same-role subtraction, unknown role names grant nothing (fail-closed); assignments union across org → account → route scopes; effective privileges recomputed per decision over the active config revision + the binding's `initiator` (stateless — a config edit takes effect on the very next message, which is how revocation works).

**Principals: user identity mapping.** User records live in the config — a `users:` section in `channels/policy.yml` (one record per person: `username` as the principal key, a display `name`, and an `identities` list of `<channel>:<provider-id>` — `slack:<id>`, `telegram:<chat id>`, `email:<address>`, …), so the mapping is reviewable in the same revision as the roles it feeds and live-reloads with it. Each identity belongs to exactly one user (duplicate → compile error). Assignments name the principal either way: `user:<username>` (all of that user's identities) or a raw channel identity, which resolves to its user when mapped and stays an anonymous principal otherwise. The same person's Slack and Telegram identities are the same user; an identity in no user's list is its own (anonymous) principal (deny-by-default via `defaultRoles`). `clisbot users` is the ops surface for listing and editing these records (thin client to the Hub control-plane API). This supersedes the per-account identity table sketched earlier: per-account tables remain the lookup index, the user record is the source of truth.

**Resource grants: user × daemon/project/agent hierarchy.** Besides the channel-side privileges above (route-scoped, T3Claw algebra), each user holds **resource grants** over the daemon side, following the daemon's own hierarchy: which **daemons** are accessible, and within a daemon which **projects**, which **agent sessions**, and which **surfaces** (terminals, files, …). At P0 there is **no daemon-side grant enforcement** — every Hub form's access is its ordinary pairing itself (§14.7), and user pairing is the stock binary-trust flow; grants are recorded in the Hub (the principal records + the pairing links it mints) but the daemon does not act on them yet. The P1 daemon grant engine (§4-S3) is where these records become enforced, coarse daemon-level first, then project/agent/surface scoping on the same records without a model change.

**Pairing links: two tiers.** Today pairing is binary trust — the daemon distinguishes paired from unpaired, not which user (`SECURITY.md`: the pairing link is the trust anchor, the phone keypair is ephemeral, no persistent per-user secret on the daemon). At **P0 the plan runs tier 2 only, for both forms**: user pairing is the stock binary-trust flow, and the daemon has no grant check. The per-user tier 1 mechanism below is the **P1** delivery vehicle for the grant engine (§4-S3), minted by the Hub and enforced by the daemon.

- **Tier 1 — grant-aware pairing (P1).** A user holding a grant on daemon `D` gets a Hub-minted pairing link for `D`. The link is the ordinary offer — `serverId` + the daemon's Curve25519 public key + relay endpoint (`packages/server/src/server/pairing-offer.ts`) — plus an embedded **pairing grant**: the user's principal id, the resource scope, a short TTL, and a one-time nonce, signed by the Hub. The Hub mints from what enrollment already stores (`daemons.server_id`, `daemons.daemon_public_key`, `status: active|revoked`), and is the only process that can mint links for enrolled daemons. The client presents the grant over the encrypted channel at handshake (a new optional message, capability-gated on `server_info.features`); the P1 daemon verifies it and **binds principal + grants to the session** — the daemon now knows _who_ is paired and _what_ they may do. Coarse "access to this daemon" first, then the fine project/agent/terminal scope.
- **Tier 2 — no grant check (P0, and the stock-daemon path).** The daemon does not verify a grant, so pairing is byte-for-byte today's upstream flow; the embedded grant, if present in the link, is simply never consumed. This is both the **P0** behavior and the required compatibility path to a stock daemon: **zero stock-daemon or stock-client change**, and a fusion user can still pair to a plain Paseo daemon.

Tier 1 is backward-compatible by construction when it lands: the offer is a pure `zod` object (`packages/protocol/src/connection-offer.ts`), so the grant is an additive optional field — an old client parsing a new link strips it and pairs normally. The handshake grant is a new optional message gated on a capability the old daemon does not advertise (`docs/protocol-compatibility.md`: new fields optional, never narrow/remove/require, gate once on `server_info.features.*`). The one-time nonce plus revocation makes a link single-use and recallable.

The P0 channel-side catalog is small (`bot.interact` to start conversations; `approval.command`, `approval.file`, `approval.config`, `approval.command.destructive` for S6's `require` decisions; owner/admin hold `*`), and the shape already carries T3Claw's full catalog (`tool.*`, `channel.tool.<name>`) for P1. The Hub's existing allowlist-only `from_users` filter stays as a compile-time safety floor for trigger _launches_; the route policy is the operational layer on top of it. The full brief this section adapts is recorded in §15.

### S5. Sync policy per route (P5)

`sync.inbound.enabled` + `sync.outbound.{finalAnswers, progress, reasoning, toolCalls, threadLink}`, per account default with route overrides. T3Claw's schema was `{finalAnswers, progress, toolCalls, threadLink}` with defaults `finalAnswers: true`, `progress`/`toolCalls` off, and `threadLink: "full"` (a three-valued `full | final-only | none`, not a boolean); this plan keeps the shape, adds `reasoning` (the Paseo timeline already carries `reasoning` items the client renders, and operators will want to gate thinking blocks per route), and moves the P0 default to `progress: true` — a channel is often the _only_ surface the operator watches, so "final answer only" leaves a multi-minute run looking dead; the progress posts stay throttled snapshots (S5 caps), never a stream mirror. `reasoning`/`toolCalls` stay off by default. Not a mirror of every timeline event: the relay mapper emits a fixed event kind set, and policy selects which kinds cross the boundary; per-kind caps (progress snapshot count/length, tool-detail length — T3Claw's `MAX_PROGRESS_*`/`MAX_TOOL_DETAIL_CHARS` discipline) ride with the channel vertical, not the policy. `threadLink` appends the back-link to the live Paseo session so the thread is never the only surface.

### S6. Tool approval: rules, authority, native UX (P6, P8)

Adapted from T3Claw's validated model (`clisbot-channel-host` `decisions.ts`/`policy.ts`/`ApprovalGate.ts`), re-derived on Paseo's richer permission primitives.

- **Decision model.** Each route carries an `approval` block: first-match-wins `rules[]` (match on `action`, `command` glob, `path` glob, resource `tag`, `tool` name — all present matchers AND) whose `decision` is `allow`, `deny`, or `{ require: <privilege>, initiatorOnly? }`, plus a `default` (`deny` or `{ require }`). `classifyRequest` maps a request to one decision; `evaluateApproval` then decides what one responder's answer does: `allow`/`deny` auto-respond immediately (no prompt, attributed to policy), `require` approves iff the responder's effective privileges cover the required one — an approver without it is **inert** (zero side effect, request stays open), and `initiatorOnly` further restricts to the thread initiator with the owner/admin override. Everything fails closed.
- **Classification inputs.** T3Claw taps provider stream args in memory (bounded map, per open request) to get the command string / path for glob matching, and can classify coarsely without args (`noArgTap` compliance switch rejects configs that need args they forbid). On Paseo this tap is not needed for most rules: `AgentPermissionRequest` already carries `kind` (`tool`/`plan`/`question`/`mode`/`other`), `name`, `input`, and `detail` (`ToolCallDetail`) — the request is self-describing, so command/path classification reads the request object instead of a passive stream tap.
- **Response power.** T3Claw's answer set was accept/decline plus a session-scoped allow-always and cancel, with no parameter editing (the response surface is `requestId` + a decision enum — its foundation's limitation, T3Claw audit Gaps item 2). Paseo's `AgentPermissionResponse` is not: `allow` can carry `updatedInput` (edit the parameters before allowing) and `updatedPermissions` (scope the grant — "acceptForSession" semantics), and `deny` can carry `message` + `interrupt`. The channel decision set is therefore `{allow [with edits], allow-always, deny, deny-and-stop}`, mapped onto `respondToAgentPermission`; P0 ships the plain decisions, edits/scopes are P1 when the native card grows a params editor.
- **Two authority checks** (T3Claw's correctness spine, kept): inbound entry — `authorizeInteract`/`authorizeAction` before anything reaches a bound session; approval exit — the responder is re-authorized by `ChannelPolicy` at dispatch time, re-deriving current rules (a revoked role takes effect immediately; the registration grants nothing by itself).
- **Native UX, phased.** P0: text prompt with command/path + required privilege + who-can-approve list, replied with `approve <requestId> [decision]` (T3Claw's message-action shape). P0.5: `ChannelPlugin.approvalCapability` renders the native card (Slack Block Kit, Telegram inline keyboard, Google Chat card) — the Hub control plane composes the content, the channel vertical renders; on resolution the already-delivered card is updated in place (T3Claw's `NativeApprovalResolutionDelivery`: "✅ Approved once by @user"). A request resolved outside the channel (Paseo client) still lands as a resolution update.

  **Decision (2026-08-27): the native approval card is P0 for Slack + Telegram.** The two-surface approval goal — a pending tool permission answerable from the channel thread AND from any paired Paseo client, exactly-once — pulls the card into P0 for the in-repo verticals: the card is placed by the account file's `transport.inlineButtons` (already in the P0 config schema), and the text + command prompt stays where the placement excludes the surface. The in-place resolution update ships with the card. The card extends the drive surface both ways — rich post + message-update outbound; button callbacks inbound (Telegram `callback_query` in the existing `getUpdates` poll, Slack `interactive` envelopes over the existing Socket Mode connection) — and the button carries no authority: the answer runs the same `answerFromChannel` second authority check as the typed command. Zero daemon diff is unchanged. This supersedes the P0.5 placement only for the P0 channels; the Google Chat / Zalo cards stay P0.5/P1 with their channels. Record: implementation doc §4.3.3 decision block.

- **Mode.** Route `approval` overrides the agent's config wholesale; per-route `mode: strict | hybrid | balanced` controls how much of the provider's own per-tool allowlist auto-approves beneath the channel (T3Claw's `t3Mode`; default `strict` — the channel layer is the gate).

### S7. Isolation (P10, P13)

Kill switches, split by phase. **P0** is Hub-side, three config levels plus the env flag — global env `CLISBOT_HUB_CHANNELS_ENABLED` (internal `PASEO_HUB_CHANNELS_ENABLED`, §14.8; supervisor env, restart) > `enabled: false` in the active `channels/policy.yml` revision (the whole control plane) > per-channel `channels.<channel>.enabled: false` (every account of that channel: its transports, ingress routes, and relay) > per-account `enabled: false`. The global flag off means the Hub loads no channel code, ingests no channel events, applies no channel policy, and stops connecting to the daemon as a channel client — byte-equivalent to today's Hub; the config levels are live-reloaded with the revision. The daemon needs **no** channel kill switch at P0 because it has no channel code (the trusted-client path is the stock local-client path). **P1** adds the daemon side: the grant engine is off-by-default and flag-gated, so flag-off the daemon behaves byte-equivalently to upstream (verified per CLAUDE.md "verify both states"). Isolation for third-party channel code (P13, §14.5 decision) is per-channel separate installs + integrity pinning + load-trace at load (§6), not a process boundary: a channel fault takes down the Hub, which is exactly why §14.5 condition 2 (an external supervisor for the Hub) is required, not optional.

### S8. Configuration, secrets, operations (P12)

All channel configuration lives in the **Hub config bundle** (§4-S2): the `.paseo/channels/` authored directory — `policy.yml` (`roles` + org-scope `assignments` + defaults) and one file per account (identity, `transport`, `policy`, `defaults` incl. `interaction`/`binding`/`reply`, `routes[]` (match + session-or-workflow target + per-route overrides + route-scope `assignments`), `fallback`) — compiled and revisioned by the existing compiler, so channel config gets Hub's revisioning, audit hash, and deploy flow for free (full shape + enum tables + the message→session mapping guide: implementation doc §4.3). Secrets in a Hub-owned secrets file via `secretRef` (0600), never in the bundle or the Hub's own env. Live reload = compile a new revision; policy/routes reload in place, while changes that add, remove, or bump a channel install are applied by restarting the Hub (module cache) — the daemon is never touched. Operations surface: the merged `clisbot` binary's channel groups (`clisbot channels add|list|status`, `clisbot users list|show|add|edit` for §4-S4's user records — mutating the active revision — and `users pairing` for pairing-link minting; the daemon does not yet act on the embedded grant) — thin CLI-side HTTP clients to the running Hub's control-plane API, implementation doc §1.4/§3.2 — plus the existing Hub diagnostics; the upstream CLI package itself learns nothing about channels beyond those new additive groups. P0 introduces **no new daemon RPCs**; any P1 grant-engine RPC follows `docs/rpc-namespacing.md`.

### S9. First-mention minting applies a workspace template (P11)

An unbound thread that creates a workspace carries the route's optional template id; the gap doc's workspace-template seeder does the rest.

### S10. Trust posture: channel-originated sessions are `approval-required` by default (P15)

External text is data, not instructions, and a channel-driven session never auto-executes sensitive tools (T3Claw fixes `runtimeMode: "approval-required"` as a hard invariant of channel-originated threads — set literally on `thread.create`/`thread.turn.start` in its coordinator, not a configurable default). The route can relax to per-tool pre-approval via policy as trust is earned. Hub stays out of scope for injection defense, as upstream documents it.

```text
  ┌─────────────────────────────────────────────────────────────────────────────┐

  └─────────────────────────────────────────────────────────────────────────────┘
```

Claims this diagram encodes:

1. One control plane: configuration, authorization, thread bindings, relay, and approval rules all live in the Hub; the daemon's P0 diff is zero (§4-S3).
2. The daemon is the single owner of agent sessions; channel-originated sessions produce timelines the clients see natively — no second brain, no bridge UI.
3. **Both forms** drive agents through the **existing trusted-client RPCs** (create / steer / permission-respond) with no new protocol — embedded over loopback, team/remote over the relay (§14.7). The upstream scoped `hub.execution.*` channel is frozen legacy-compat, not a form's design path.
4. Channel code runs **in the Hub, in-process** (§14.5), per channel: the failure domain is the whole Hub, which is why the Hub needs an external supervisor (operator-provided at P0; the optional daemon-managed form is P1) and why the daemon is the one process a channel can never reach.
5. The embedded and team forms share the same control-plane code and the same wire (ordinary-client `scopes: ["*"]`, §14.7) but differ in database backend, deployment location, **and trust posture** — embedded is a full-trust loopback client (same trust domain as the daemon); team is a full-trust relay client whose blast radius the P1 grant engine narrows. P9's "one system" means _one codebase, one wire, two deployment locations_, with full parity at P0 and per-principal scoping at P1.

### Load-trace check

Each channel is installed to its own directory and loads its pinned `openclaw/*` / `@openclaw/*` modules into the Hub. At load, the Hub checks the channel's loaded set against the matrix: allowed = {the channel's own dist (+ its bundled `node_modules`) and the matrix-allowlisted pure subpaths of the pinned main package} — or, for the inlined bundled channel, just its own dist directory (§7). Anything else is a matrix miss and fails the channel's account at load. The static half of the surface-matrix discipline, run at module load instead of at a child process's spawn (§14.5).

## 7. The channel seam

**Post-pull scope (2026-08-26):** this seam now serves **pinned** channels only. With the in-repo pull, Slack's alias routing disappeared with its vertical and Telegram stopped loading as the bundled dist — the in-repo verticals are seam-free (zero `openclaw/*` specifiers; inbound calls `hostRuntime.onInboundReply` directly — [2026-08-26-in-repo-channel-verticals.md](2026-08-26-in-repo-channel-verticals.md) §6.5 rule 1). What follows describes the pinned supply's contract, still load-bearing for zalouser's pinned dists and later pinned channels; the dist baseline it was verified against is the [`pinned-vertical-contracts`](pinned-vertical-contracts/README.md) folder.

Two loading modes, one host contract. "Host" here is the **Hub** — OpenClaw's term for the process that loads a channel plugin; since §14.5 it is in-process, so "host" and "Hub" are the same process and the seam's bound subpaths resolve to Hub modules directly, with no IPC boundary. Every channel entry injects the host runtime through its setter (`setSlackRuntime` for published Slack, `setChannelRuntime` on the bundled Telegram entry — verified on both). What differs is where the pure-logic SDK code lives:

- **Published channels** (Slack, Google Chat, Zalo, …): the dist imports `openclaw/plugin-sdk/<subpath>` externally. The Hub's alias hooks bind the bound subpaths to Hub modules; allowlisted pure subpaths resolve to the pinned main package. The matrix classifies each imported subpath.
- **Bundled channels** (Telegram): SDK **inlined** into the main package's `dist/extensions/telegram` — verified zero `plugin-sdk` import specifiers, so no alias surface at all. Loads by `file://` URL against the installed main package; the host contract is purely the runtime setter. Matrix records "inlined build, no seam"; load-trace allowlist is its own dist directory.

Classification rule (published channels): **passthrough** when the import graph stays in pure SDK code; **bound** when the host must supply behavior (agent loop, sessions, config, state, gateway); **unsupported** (typed throw, T3Claw's pattern) when neither applies this phase.

Bound subpaths for P0 (working table; the full matrix is generated by the audit, not hand-listed):

| Subpath                                                            | Bound to                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `channel-inbound`                                                  | the Hub's per-account ingress route (webhook) or the channel's own transport (Socket Mode / polling) → the channel's own verification + normalization (its dist's `webhook-ingress`/`webhook-request-guards`) → typed event to the trigger-run dispatch in-process (media via the pure `buildChannelInboundMediaPayload` → Paseo attachments; unsupported media types decline gracefully) |
| `channel-outbound-runtime`, `channel-outbound`                     | outbound requests from the Hub relay (in-process calls) → the channel's own `message`/`outbound` adapters                                                                                                                                                                                                                                                                                 |
| `plugin-state`, `session-store-runtime`                            | Hub-owned durable state (thread bindings, route state) in the Hub DB (§4-S2); channel code is stateless across restarts                                                                                                                                                                                                                                                                   |
| `agent-runtime`, `session` (turn-side), `gateway`/`gatewayMethods` | Hub modules directly — OpenClaw's agent loop and gateway never load                                                                                                                                                                                                                                                                                                                       |
| `secret-file-runtime`, `config-mutation`                           | the Hub's `secretRef`-backed secrets file; config mutation unsupported in P0                                                                                                                                                                                                                                                                                                              |
| `channel-pairing`, `heartbeat-runtime`, `reply-runtime`            | unsupported in P0 (DM access enforced by the Hub channel policy, §4-S4; replies flow through the relay)                                                                                                                                                                                                                                                                                   |

Everything the conformance probes passed — `routing`, `text-chunking`, `dedupe-runtime`, `keyed-async-queue`, `channel-status`, `status-helpers`, `webhook-ingress`, `webhook-request-guards`, … — stays OpenClaw's. Core-owned behaviors that live in the gateway rather than the published import graph (e.g. posting the in-turn status reaction) are control-plane responsibilities, driven through the channel's `actions` adapter in-process, P1.

## 8. Native formatting per channel

The Hub composes (which text, which progress snapshot, which approval card); the channel's published code, running in-process (§14.5), renders it natively. Neither composes native channel content on the Hub's side, and updates ride the pin manifest.

- **P0 — text + progress, natively formatted.** Slack mrkdwn/Block Kit (native markdown blocks for pipe tables, progress blocks), Telegram HTML with edit-in-place draft streaming, Google Chat cards.
- **P0.5 — native approval cards** via `approvalCapability` (§4, S6).
- **P1 — agent-authored native content** (raw blocks through `blocks-input`), policy-gated.
- Per-channel limits (Zalo's weaker markup, Discord embeds) are channel-owned; the Hub stays agnostic.

## 9. Adding a channel: the procedure

**Two supply routes after the 2026-08-26 pull.** The steps below are the **pinned** route — what zalouser and later channels go through. **Slack and Telegram no longer go through this procedure**: they are in-repo packages ported once (blueprint [2026-08-26-in-repo-channel-verticals.md](2026-08-26-in-repo-channel-verticals.md) §6.5) and then re-synced via that doc's §4 loop (bump the sync reference, diff the `SYNC.md` manifest, walk `DEVIATIONS.md`, contract gate + live E2E). A future channel may be pulled in-repo the same way (the pull was designed to generalize — that doc §2.2 + §7: zalouser reuses the §4 mechanics with the Clisbot reference surface); the route is a per-channel decision, not fixed by this procedure.

The hard gate is T3Claw's, re-pointed: **if a new channel needs a change to the control plane (config compiler, channel policy, relay, or approval engine) or the channel seam (§7) beyond the surfaces this plan defines, stop — add that capability with its own conformance test in a separate change, then retry.**

1. Add the package + `dist.integrity` (+ `gitHead` when published — channel packages do, the main package does not) to `channel-pins.json`; install from the public npm registry.
2. Subpath audit: static import-graph classification of the channel's dist against the matrix; every new subpath lands as passthrough / bound / unsupported with a reason.
3. Import conformance: all named imports resolve against the pinned main package.
4. Wire transport: Socket Mode / polling need nothing; **webhook channels add a per-account route on the Hub's existing ingress** — the same pattern as today's `/webhook` (GitHub) and `/api/integrations/slack/events`: the Hub's web server owns inbound HTTP and opens the only ports; the route hands the raw payload to the channel's own signing checks (`webhook-request-guards`, in-process — §14.5) before the verified typed event reaches the trigger-run dispatch. In the team form the Hub is already publicly reachable (that is how GitHub webhooks arrive today); in the single-machine form the operator's reverse proxy/tunnel fronts the same Hub surface (§14.2).
5. Define the thread-binding key for the channel's conversation shape.
6. Fake-transport conformance test (bind → session → reply → follow-up resume) into CI.
7. `THIRD_PARTY_NOTICES` entries for the channel's bundled deps; docs row.

### Effort estimate: lines of code, not wall-clock time

Estimates here are in generated lines of code, because wall-clock time for AI-coded work depends on inference throughput and how many sub-agents run in parallel — not a stable planning unit. The estimate is only useful if it separates what machines do for free from what an agent must generate:

| Step                                                                     | Who does it                                                                                      | Cost                                                 |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------- |
| Transport, auth, native rendering, chunking, media, reactions, lifecycle | OpenClaw, prebuilt in the published dist                                                         | 0 lines                                              |
| Steps 1–3 (pin, matrix, conformance)                                     | Machine: the audit + conformance tooling generates and checks; the diff is reviewed, not written | 0 generated lines; ~10–50 line diff to review        |
| Step 4 (transport wiring)                                                | Socket/polling: 0; webhook: one route registration on the existing ingress                       | 0–30 lines, and only when the ingress surface exists |
| Step 5 (thread-binding key)                                              | Agent                                                                                            | ~10–30 lines                                         |
| Step 6 (fake-transport conformance test)                                 | Agent — the main generated block per channel                                                     | ~100–200 lines                                       |
| Step 7 (notices, docs)                                                   | Agent                                                                                            | ~10 lines                                            |

So a new channel is **O(100–300) generated lines, mostly test code**, plus a machine-checked diff — against thousands of lines for option D. Steps 2–3 are independent per channel, so N channels can proceed in N parallel sub-agents; wall-clock scales with the largest single channel plus throughput, not with N × effort. T3Claw's measured pace (two verticals in two days of work, §2 P2) is consistent with this: the generated block was small, the review was the bottleneck.

## 10. CI gates and acceptance

- **Subpath audit (static):** every `openclaw/plugin-sdk/*` import in pinned channel dists is classified by import graph; unclassified or reclassified subpath fails CI. T3Claw's audit, actually wired in from day one.
- **Import conformance:** all named imports of all pinned channels resolve against the pinned main package (verified 2026-08-23: Slack 331/0, Google Chat 124/0, Zalo 127/0); plus the `compat.pluginApi` floor.
- **Load-trace check:** each channel's loaded module set stays inside its allowlist, checked at load (§6).
- **Supervisor demonstration (§14.5 condition 2):** kill the Hub with a channel loaded; the external supervisor (operator-provided at P0 — systemd/`pm2`/launcher) restarts it; thread bindings and the delivery ledger resume from `PASEO_HUB_DATA_DIR` with no double-post.
- **Transport:** the Hub's daemon-transport is ordinary-client-only (no scoped path) — embedded pairs over loopback; team/remote pairs over the relay (§14.7). Acceptance covers both: the loopback form and a relay-paired form against a non-local daemon (the relay-pair case exercises `attachExternalSocket` → `scopes: ["*"]`, same scope set as a phone; `websocket-server.ts:1342/1391`).
- **Orphan recovery (the create-then-crash window):** create the agent, kill the Hub before it persists the binding, restart; the Hub finds the unbound agent via its pre-create marker and **rebinds instead of re-creating** — one agent, no duplicate (the trusted-path substitute for the scoped create-dedup, §4-S2).
- **Prompt-injection backstop:** a channel session whose prompt tries to drive a native tool (Bash/Edit/Write) stalls at `permission_requested` until a policy/route-approved responder answers — and the agent-injected `paseo` MCP `respond_to_permission` tool cannot self-approve under the default provider permission config (§4-S10).
- **Fake-transport conformance per channel**; **P0 live acceptance** reuses T3Claw's case shape: bind, follow-up resume, restart/resume, policy denial, flag-off byte-equivalence, two-authority-check proof — plus the relay/approval cases: final answer posted while progress/reasoning stay off (per-kind sync), throttled progress when enabled, tool-call lines only under `toolCalls`, restart does not double-post (ledger dedupe on stream replay), `allow`/`deny` rules auto-respond without a prompt, `require` prompt in-thread with an inert wrong approver and a landing privileged approver, approval card updated in place on resolution (P0 for Slack/Telegram from 2026-08-27; other channels P0.5). Flag off: no channel code loaded, no channel ingress routes, no channel config read, no channel client connection from the Hub — the daemon is **byte-equivalent to upstream Paseo because it has no channel code at P0** (there is no dormant daemon piece to switch).

## 14. Decisions and open items

1. **Upstream ownership of the wire additions — re-scoped by the §14.6 pivot (2026-08-24), closed by §14.7 (2026-08-25).** This decision originally covered two new `hub.execution.*` RPCs (`agent.steer`, `agent.permission.respond`) and the pairing-grant handshake. The §14.6 pivot **removed both from P0**: thread continuity and approval exit now ride the **existing** trusted-client RPCs (`send_agent_message_request` with `activeTurnBehavior: "steer"`, `agent_permission_response`), and pairing is stock binary-trust. §14.7 closed the residual question ("grant-scoped RPCs if the team form needs steer/permission-respond on the scoped channel"): the team form does **not** need them — it pairs as an ordinary client and uses the same trusted-client RPCs as the embedded form, so **no new RPCs of any kind remain in the design**; the only wire addition is the **P1 grant engine's principal binding** (an additive optional handshake message, capability-gated on `server_info.features` + an additive optional offer field, the pairing grant). The original decision stands for that surviving surface, narrowed:
   - **Kept Clisbot-side, written to be promotable** — `COMPAT`-tagged, optional fields only, pure wire schemas; the grant engine is the one place the fork's protocol divergence is allowed to live, and it is deliberately the fork's largest upstream surface (§4-S3 P1). Re-check upstream at every merge: if upstream ships a per-device pairing policy or a per-resource grant model, converge names and semantics early instead of forking the same concept.

   Rationale unchanged: promotion-readiness is cheap because P10's compatibility rules are the same rules a promotable piece needs; and with P0's wire diff at zero, the only surface that can ever block a clean `upstream/main` merge is the P1 grant engine — so it gets the most discipline (self-contained module, additive hunks, tests that pass unchanged against `main`). Cross-link: §14.3 (Hub-side modules) and §14.6 (the pivot decision).

2. **Webhook exposure is an operator decision** (§9, step 4). No new mechanism: the Hub's web server already accepts provider webhooks publicly in the team form (GitHub signed webhooks at `/webhook`, Slack events at `/api/integrations/slack/events`) — channel ingress routes are the same exposure class, so the team form needs nothing new beyond the routes themselves. The open call is the **single-machine form**: who fronts the Hub surface for the operator's reverse proxy/tunnel (their infrastructure in P0.5), and whether the Hub later ships a first-class tunnel/marshaling story. Verification is per channel route: the channel's own signing checks (`webhook-request-guards`) run in the owning vertical before a payload reaches the Hub's dispatch, so an unverified route cannot trigger runs.
3. **Upstream contribution for the channel control plane.** The Hub extensions (§4-S2) are larger than the wire additions: a new authored config block, multi-account connections, thread bindings + continuous execution, the outbound relay + delivery ledger, and the approval engine. They can live in the same two places as §14.1:
   - **Contributed upstream** — the Hub mainline gains the channel control plane; this fork keeps only Clisbot-specific deltas (e.g. the OpenClaw vertical seam) and shrinks with every merged piece.
   - **Kept Clisbot-side** — the extensions live in this fork only; upstream Hub stays a trigger-only product, and every `upstream/main` merge carries the extension diff.

   **Decision (2026-08-24): keep all of it Clisbot-side for now, but write every module to be promotable — the same posture as §14.1, applied to the Hub side.** No PRs in advance; each module is lifted out when it is ready. Promotion order by independence (lowest coupling first): the `channels:` config block + multi-account connections (pure Hub, no daemon change), then thread bindings + continuous execution, then the outbound relay + delivery ledger, then the approval engine. The one daemon-side candidate is the additive `paseo.json` workspace-template field (gap doc).

   To make promotion cheap, the fork work follows the same rules as §14.1: modules stay self-contained (each compiles and tests without fork-specific imports beyond the config compiler), config/DB additions stay additive with clean migrations, and behavior is covered by tests that would pass unchanged against Hub mainline. The modules are also written against the Hub's existing seams (config compiler, `OutputExecutorRegistry`, `DaemonExecutions` contract) rather than parallel machinery, so a promoted module is a Hub module, not a Clisbot module rebadged.

   Rationale: the channel control plane is the part most likely to become an upstream Hub feature in its own right (thread-bound agents, approval forwarding are generic needs, not Clisbot-specific ones), so keeping it promotable from day one is worth the discipline; it is also the part where diverging hardest would cost most to merge back.

4. **Tarball supply — decided: pin the public supply directly, no mirror (2026-08-24).** Integrity pinning (`channel-pins.json` → `dist.integrity`) protects against _tampering_; the residual risk is _disappearance_ — OpenClaw unpublishes/deletes a pinned version, stops publishing a channel, or the registry has an outage. A private mirror (registry + retention policy) would close that, but is assessed as **low risk for now and not worth the machinery**:
   - The pin moves with releases: the channel pin is updated on the OpenClaw update cadence anyway (conformance + `compat.pluginApi` floor gates catch drift), so a pinned version is a moving target, not a bit-for-bit archive — long-term reproducibility was never the goal.
   - The failure has a cheap recovery: re-pin to the latest public release (CI gates prove it), and if the pinned version is gone from npm, the public git repo at the recorded `gitHead` is the fallback supply behind the identical seam interface; option A (vendored source) is the escape hatch behind the same interface.
     Revisit only if the failure actually bites (a pinned version disappears with no acceptable re-pin) or if support/reproducibility requirements make installs need to resolve offline.
5. **Vertical process model — decided: in-process in the Hub, with two mandatory conditions (2026-08-24).** Context: the plan originally ran each channel vertical as a Hub-supervised child process (typed IPC: inbound events in, outbound text out, supervision out). Rationale was blast radius (P13): a third-party dist fault should not take down the control plane.
   - **Option A — per-channel child processes (the original design).** Isolation is complete (a hang/leak/native crash in one channel can only kill its own process); a pin bump restarts one channel; per-account load-trace is a runtime assertion. Cost: a vertical IPC contract, a vertical supervisor, and a second process per channel to install, update, and diagnose — for a P0 where one operator watches one machine.
   - **Option B — in-process in the Hub (chosen).** No IPC contract, no supervisor, one install surface; each channel is still installed separately (own dir, own pin, own tokens, load-trace at load), so per-channel install/replace stays true; the seam table (§7) binds subpaths directly to Hub modules. Cost (accepted): a channel fault — including an event-loop hang, which no in-process catch handles — takes down the whole Hub: relay, bindings, ledger, RBAC, and every other channel.
     Decision: **Option B, with two conditions that make the accepted risk operable:**
   1. **Per-channel separate install + load-trace at load.** Each channel installs to its own directory from its pinned, integrity-verified tarball; at load the Hub checks the channel's loaded module set against the matrix allowlist (the static half of §6, checked at load instead of at spawn); a channel's code has no filesystem reach beyond its install dir and no credentials beyond its own channel tokens.
   2. **An external supervisor for the Hub — required, not optional.** In-process means nothing inside the Hub can restart the Hub, and P0 ships no built-in supervisor for the embedded form. The first-class form is the daemon-managed embedded Hub (§4-S3: spawn + backoff + crash-loop breaker on the managed-process registry); before that lands (P1), the operator provides one (systemd unit, `pm2`, or the like) — acceptance (§10) requires the supervisor to be demonstrated, not configured.
      Rationale: at P0 scale (one person, one machine, a handful of channels) the failure mode the child process bought — "channel A takes down channel B while the control plane keeps running" — is not the one that hurts: agent sessions live in the daemon and are never in the Hub's failure domain, thread bindings and the delivery ledger are durable in `PASEO_HUB_DATA_DIR` (record-before-post), and a Hub restart is one supervised restart away. T3Claw already ran channel code in-process for two working channels — this decision re-adopts that posture deliberately, with the load-trace + external-supervisor conditions that T3Claw did not have.
      Revisit trigger: move channels back out to per-channel processes when (a) the team form is served (multi-user: one channel's fault must not stop every member's relay and approvals), or (b) a pinned channel actually exhibits a hang/leak in the field — whichever comes first. The seam table and load-trace are transport-agnostic, so that move is a supervisor + IPC addition, not a re-architecture.
6. **Hub→daemon transport — decided: P0 trusted-client, no scoped fork channel; the scoped approach is obsolete for P0 (2026-08-24).** Context: the plan's P0 shipped the embedded Hub on an enrolled `hub.execution.*`-scoped loopback connection (transport "option A"), and the fork's daemon diff was three additive pieces — two new `hub.execution.*` RPCs, a managed-process slot, and a grant-aware pairing handshake. The owner questioned that design: (a) it adds non-trivial logic to the daemon when the goal is the smallest possible daemon footprint; (b) the scoped namespace is not where a malicious channel message is stopped — that happens at the agent layer (toolPolicy + approval-required + S6 rules); (c) the per-user/per-resource authorization is cleaner as one P1 grant engine that narrows every session than as a P0 pairing-grant side-channel on one transport.
   - **Option A (pre-pivot) — scoped fork channel.** Enrolled `hub.execution.*` session + two new RPCs + pairing-grant handshake. Pros: least privilege by construction at P0, team form gets full capability early. Cons: daemon diff (a scoped attach path, new RPCs, a grant verifier, a `server_info.features` flag) on the exact surface P10 works hardest to keep clean; two-sided wire-schema lockstep on every merge; a second trust class readers must hold in their head.
   - **Option B (chosen) — P0 trusted-client; P1 grant engine.** Embedded Hub connects as the local CLI/app does (loopback `hello` → `scopes: ["*"]`) and uses the existing RPCs named in §4-S3. _(Refined by §14.7, 2026-08-25: the team/remote Hub now pairs as an ordinary relay client — the same `scopes: ["_"]`, `kind: "trusted"` a phone has — so both forms use Option B's RPCs; the scoped channel is frozen legacy-compat, expected to sunset.)\*
     **Decision (2026-08-24): Option B.** Consequences accepted and made structural:
   1. **P0 channel capability is embedded-form-only.** Steer + approval exist only on the trusted path; the team/remote form is create + control until P1. _(Superseded 2026-08-25 by §14.7: the team/remote form now pairs as an ordinary client and has steer + approval at P0; the grant engine P1 narrows rather than unlocks.)_
   2. **The trusted transport mode is loopback-only** — the Hub's transport adapter refuses it against a non-loopback daemon origin and falls to the upstream scoped path. _(Superseded 2026-08-25 by §14.7: non-loopback daemons are reached by ordinary relay pairing, not the scoped path; full trust is bounded by the P1 grant engine on both forms.)_
   3. **The Hub owns idempotency** — a durable executionId↔agentId thread-binding ledger + pre-create marker + orphan recovery on restart (trusted `create_agent_request` has no dedup; the scoped path's `findByDaemonExecution` dedup is not on this path). Orphan-recovery is a P0 acceptance case (§10).
   4. **The P1 grant engine is the fork's largest upstream surface and P9's gate** — a cross-cutting principal + resource grant over `agentManager`/workspaces/terminals/files/config/checkout, additive + capability-gated + flag-off byte-equivalent, dedicated module, promotable per §14.1/§14.3. P0's daemon diff is zero; P1's is real and is managed as such.
   5. **Prompt-injection posture unchanged**: the socket scope was never in the injection chain; the backstop is the agent layer (provider permission system — native tools not pre-approvable via `toolPolicy` — + S10 `approval-required` + S6 two authority checks), with the acceptance backstop case covering the agent-injected `paseo` MCP `respond_to_permission` tool.
      Rationale: the controlling constraint was the smallest possible daemon footprint — P0 becomes `packages/hub` + CLI groups with no protocol divergence; the over-privilege concern is answered more completely, and for all clients, by the P1 grant engine. Nothing in upstream changes as a result.
      Revisit trigger: if the P1 grant engine's blast radius proves larger than estimated, the scoped fork channel (option A) can be resurrected for the team form without touching P0 — the obsolete note in §4-S3 records exactly what that would mean.
7. **Team/remote form rides the ordinary client wire; the scoped channel is frozen legacy-compat, expected to sunset (2026-08-25).** Context: §14.6 kept the team/remote form on the upstream scoped channel (create + control only) at P0. The owner directed that the team/remote form should also ride the ordinary client wire, for two reasons the code verifies: (a) a relay-attached socket is already `scopes: ["*"]`, `kind: "trusted"` — the same scope set a phone has (`websocket-server.ts:1342/1391`; `attachExternalSocket` → `attachSocket` → `createSessionConnection`) — so a team/remote Hub that pairs like a client gets steer + approval with **zero** daemon change; and (b) the scoped namespace is not the security boundary — `agent_permission_response` has no owner/kind check (only `requireAgent(agentId)`) — so the scoped channel bought no security the P1 grant engine (§4-S3, which narrows _any_ bound-principal session) doesn't buy better and more uniformly.
   - **Option A — keep the team form on the scoped channel until P1.** Steer + approval deferred to P1; the team form is create + control at P0. Cons: a second trust mode readers must hold in their head; the team form is functionally crippled at P0; the scoped channel must be maintained as a live path.
   - **Option B (chosen) — both forms pair as ordinary clients; scoped channel is frozen legacy-compat.** The team/remote Hub pairs over the relay like a phone (`scopes: ["*"]`), using `create_agent_request` / `send_agent_message_request` + `steer` / `agent_permission_response` — the same RPCs the embedded form and the app use. The upstream scoped channel is kept **untouched** only so existing enrolled daemons keep working, and is expected to **sunset** once the P1 grant engine narrows the full-trust pairing. No form is designed to ride the scoped channel at P0.
     **Decision (2026-08-25): Option B.** Consequences:
   1. **Both forms have steer + approval at P0**, on the ordinary wire. The "embedded-form-only" limitation from §14.6 is lifted.
   2. **The security hardening is the P1 daemon grant engine, not the transport.** A full-trust Hub (embedded or team) is a full-trust client; the grant engine narrows a bound-principal session regardless of form or transport. The scoped channel is retired rather than extended, because it is not where the security lives.
   3. **The scoped channel is frozen legacy-compat and expected to sunset.** It stays upstream-untouched for existing enrolled daemons; no fork code depends on it; it is removed from the design path. Sunset is gated on the grant engine landing (P1).
   4. **No P0 daemon diff, no new wire** — unchanged from §14.6; both forms reuse the existing trusted-client schemas, so the lockstep/byte-equivalence argument strengthens (one wire, two forms).
      Rationale: one trust model (ordinary client) instead of two; the team form is not crippled at P0; the security story is cleaner and uniform (the grant engine narrows every client, Hub included); and it retires a confusing, non-protective transport rather than maintaining it. This supersedes the embedded-only limitation in §14.6 consequences 1–2 and the "scoped channel is the team form's P0 path" wording throughout.
8. **Fork env namespace `CLISBOT_*` + shared home `~/.clisbot` + local Hub auto-discovery (2026-08-25).** Context: this is the `clisbot` product, not a `paseo` rebrand, and the operator onboarding path (`clisbot daemon start` → `clisbot hub start` → `clisbot hub init` → `clisbot channels add …`) should not require setting any URL/secret env for the local case. Three sub-decisions:
   - **`CLISBOT_*` prefix, aliased to `PASEO_*` at the boundary (not a rename in place).** Operators set `CLISBOT_*`; the internal fork code keeps reading upstream `PASEO_*` names. Renaming every `process.env["PASEO_…"]` read across the forked Hub _and_ the upstream daemon would be a large diff that re-fights on every `upstream/main` / `getpaseo` merge — so the namespace is aliased, not renamed. One small module (`packages/hub/src/env-alias.ts`, Clisbot-owned) holds a fixed table and, at each process entry (the `clisbot` CLI at every spawn/local verb, the Hub's own entry for the deployed form), copies `CLISBOT_X` into `PASEO_X` **when `PASEO_X` is unset**; an explicitly-set `PASEO_X` always wins. Table: `CLISBOT_HOME`→`PASEO_HOME` (default `~/.clisbot`), `CLISBOT_HUB_DATA_DIR`→`PASEO_HUB_DATA_DIR` (default `~/.clisbot`), `CLISBOT_HUB_DATABASE_URL`→`DATABASE_URL` (default unset = embedded PGlite), `CLISBOT_HUB_CHANNELS_ENABLED`→`PASEO_HUB_CHANNELS_ENABLED` (default on; supervisor env, restart), `CLISBOT_HUB_BIND`→`PASEO_HUB_BIND` (default `127.0.0.1`, not upstream `0.0.0.0`), `CLISBOT_HUB_URL`/`CLISBOT_HUB_API_KEY`→`PASEO_HUB_URL`/`PASEO_HUB_API_KEY` (team/remote form only).
   - **Shared home `~/.clisbot` for daemon and Hub (one dir, two writers, no conflict).** Upstream kept them separate (`~/.paseo` = `PASEO_HOME`; `$XDG_DATA_HOME/paseo-hub` = `PASEO_HUB_DATA_DIR`); the fork merges both to `~/.clisbot` so there is one mental home and one place to back up. Verified no top-level entry collision: the daemon writes `agents/`, `projects/`, `worktrees/`, `config.json`, `daemon.log`, `paseo.pid`, …; the Hub writes `hub.db`, `secrets/`, `channels/`, `.paseo-hub.lock` — disjoint. This is the **machine home**, distinct from the **project-local** `.paseo/` config dir (CWD-relative, upstream-defined: `hub.yml` + `workflows/` + `channels/`, `bundle-contract.ts`), which lives in the operator's project repo and keeps the `.paseo` name — do not conflate the two.
   - **Local Hub auto-discovery; no `CLISBOT_HUB_URL`/`CLISBOT_HUB_API_KEY` to set for the local path.** `clisbot hub start` binds loopback on port **6868** (upstream is 3000; the offset keeps a stock upstream Hub and a clisbot Hub from colliding on one machine — revised 2026-08-25 from the original 3100 to the port the implementation doc settled on, §3.2/§4.6 notice 5) and writes a `hub-local.json` state file in `$CLISBOT_HOME` (url, pid — no secret, the control plane trusts loopback). The local verbs (`hub init`, `channels …`, `users …`) read that file to find the Hub; the name is distinct from the daemon's `hub-relationship.json`, so both coexist in the shared home. Auth: the embedded control plane trusts loopback clients (the Hub's existing `resolveClientAddress`/`trustedClientIpHeader` loopback-trust mechanism is reused). The Hub still auto-generates and persists its auth secret in `hub.db` (`runtime_configuration`); that secret is the credential for the **team/remote (non-loopback)** form, where the operator points the CLI at the Hub with `CLISBOT_HUB_URL` (+ `CLISBOT_HUB_API_KEY`) — the same flag → env → stored-login precedence as upstream, `CLISBOT_`-prefixed. **`CLISBOT_HUB_DATABASE_URL`** keeps a leaked shell `DATABASE_URL` out of the embedded form: the embedded `hub start` controls `DATABASE_URL` in the spawned Hub explicitly (set from `CLISBOT_HUB_DATABASE_URL` when present, else unset), so an ambient shell `DATABASE_URL` pointing at an unrelated dev Postgres cannot silently switch the embedded Hub into team mode.
     Decision: all three, as above. Consequences: the `CLISBOT_*` env surface is the operator's; `PASEO_*` remains the internal/upstream name; the kill-switch precedence (S7) is global env `CLISBOT_HUB_CHANNELS_ENABLED` (supervisor, restart) > org `enabled` > per-channel `channels.<channel>.enabled` > per-account `enabled` (the three config levels live-reload). Full shape, table, and the daemon/Hub shared-home layout: implementation doc §4.5. Team-form bootstrap vars (registration / organization creation) may be set in the embedded form without harm — the embedded P0 defaults (registration closed, one operator account) are just the single-machine setup; no embedded-only gating is needed.
     Rationale: a fork that is a distinct product (`clisbot`) should own its operator-facing namespace and defaults; the alias (rather than rename) keeps the diff small and merge-friendly; the shared home removes a second "where is my data" question; and loopback auto-discovery makes the zero-setup local onboarding real — the operator types no URL and no secret to wire the local Hub to the local CLI.
