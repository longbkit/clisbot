# Goal ledger: port OpenClaw channels into Fusion

Date started: 2026-09-07. Owner: Long Luong. Status: in progress. This file is the running ledger for the goal set in the 2026-09-06 discussion; the strategy and rules live in [the runtime strategy](2026-09-06-openclaw-channel-runtime-strategy.md) and the audits it links. Update the ledger in place, never append a diary.

## Goal (as agreed, clarified 2026-09-07)

Fusion ships the full OpenClaw channel experience with Fusion owning the code, the UX and the control plane:

1. **Slack and Telegram complete, for real users.** Every user-facing OpenClaw capability works end to end: threads/topics, mentions, formatting and chunking, native Slack Block Kit messages (rich blocks, tables, charts and other visual presentation), buttons/selects/approval and their callbacks, reactions, edit/delete/pin, polls, slash and native commands, emoji discovery, group DM, voice/video/location, and files of any type sent and received in both directions, one or many per message. Retries, receipts and error handling included. Verified automatically against the live surfaces configured in `.env`.
2. **Discord, Google Chat, Feishu/Lark, Zalo Personal and Zalo Official Bot are in scope as working channels**, not as placeholders. Each ships as a full vertical on the same platform: package layout, config/setup, capability discovery, authorization, error semantics, persistence boundary, message tool actions, channel-specific tools, and the same test contract. Everything testable without credentials is tested now; live E2E runs when credentials are provided.
3. **Upstream stays cheap to follow, by construction.** Third-party SDKs are the same ones OpenClaw uses, at the same versions (grammY, Bolt/Web API/Socket Mode, markdown-it, and each channel's SDK). Anything OpenClaw-internal that the channel code references (core helpers, plugin-sdk, workspace packages) is copied into this repo, never depended on. Copies keep upstream structure in this order: whole folder → subfolder → whole file → same functions → as many identical lines as possible; when a line must go, the remaining functions stay matching. Unused code may stay for diff-friendliness. Only concrete blockers (an OpenClaw SQLite store, a host config writer, a global runtime closure) are replaced, at the smallest boundary, and every such change is a recorded deviation. A machine-checked source manifest (`npm run channels:sync:check`) replaces the hand-written SYNC tables so the next upstream update is a delta, not a re-port.

Non-negotiable reliability: durable inbound admission before ACK/offset, persistent queue, claim lease and fencing, per-conversation lane, retry/backoff/dead-letter, restart drain, idempotent replay, outbound receipts with partial and unknown outcomes, callback ACK/authority/expiry.

Upstream baseline for this goal: `~/projects/openclaw-private` at `5d8067a4483` (OpenClaw `2026.9.2`).

## Implied scope (inferred 2026-09-07, treated as part of the goal)

The user asked for the scope to include what a complete channel platform needs even if not spelled out. These are in scope and each maps to a slice below:

- **Inbound parity, not only outbound.** Mentions, slash/native commands, button and select callbacks, message edits and deletes, inbound reactions, forwarded and quoted messages, poll answers, join/leave and topic events, and inbound media of every type, one or many files per message, downloaded within size caps and handed to the agent as attachments.
- **Conversation continuity.** Same thread/topic/DM maps to the same agent session; `/new`, `/stop`, model or agent switch, and permission approvals work from the channel; presentation fallbacks (charts, tables, buttons) degrade sensibly on channels without the native primitive.
- **Streaming and progress.** Typing indicators, draft streaming or edit-in-place where the platform allows, progress blocks, status reactions.
- **Access and policy.** DM/group allowlists, owner and admin roles, mention-only versus always-reply, per-conversation binding and pairing, multi-account per channel, per-organization isolation.
- **Setup UX.** Token and scope validation with guided fixes (Slack scopes and app manifest, Telegram privacy mode, webhook versus polling, QR login and relink for Zalo Personal, service-account and public endpoint for Google Chat, event subscription or long connection for Feishu), account identity probe, health and reconnect state visible in the app.
- **Operations.** Queue depth, dead-letter listing and resubmission, delivery receipts, diagnostics command, retention and pruning of queue rows, media temp files and caches.
- **Security.** Secret redaction in logs, webhook signature verification, callback authority (only the requester or an allowed role can approve), rate limiting and platform throttling (grammY throttler, Slack rate limits), SSRF and size limits on media URLs.
- **Compatibility and migration.** Existing Slack/Telegram Connections, bindings and config revisions keep working across the port; the new paths sit behind the channel feature flags; unmodified Paseo apps keep pairing with the daemon.
- **Verification assets.** Differential fixtures from upstream tests with provenance, extended live scenario scripts (`docs/tests/channels/p0-live-scenarios.md`), simulated-platform harnesses for channels without live credentials.
- **Docs.** Per-channel user setup guide and capability matrix in `public-docs/`, developer guide for adding a channel on this platform, and the upstream update runbook.

## Layout rules used by every slice

| Upstream root                                                                                           | Local root                                        | Package                            |
| ------------------------------------------------------------------------------------------------------- | ------------------------------------------------- | ---------------------------------- |
| `extensions/<channel>/src/`                                                                             | `packages/channels/<channel>/src/`                | `@getpaseo/channels-<channel>`     |
| `packages/markdown-core/src/`                                                                           | `packages/channels/markdown-core/src/`            | `@getpaseo/channels-markdown-core` |
| `src/agents/tools/`, `src/channels/plugins/`, `src/infra/outbound/`, `src/plugin-sdk/` (selected files) | `packages/channels/core/src/<same relative path>` | `@getpaseo/channels-core`          |

Relative paths and file names under a root stay identical to upstream. Imports are rewritten to local packages. Fusion-owned adapters (Hub store, credentials, routing) live outside these roots.

- Targeted tests only (`npx vitest run <file> --maxWorkers=1 --no-file-parallelism`); Hub typecheck once per integration, never two `tsgo` at once.
- `git diff --check` clean, Fusion-owned files formatted with `npm run format:files -- <paths>`. - Ported files carry `// upstream: <path>@5d8067a4483` on line 1 when copied; deviations listed in the package manifest, not in prose.
- No claim of support for a capability that lacks a test on the production path.
- Stage new files with `git add -A` as soon as a slice lands (untracked packages were lost once to `git clean`). Agents never run `git clean`, `git checkout --`, `git stash` or `git reset`.
