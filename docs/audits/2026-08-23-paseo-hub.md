## What Hub is

Hub is the trigger/dispatch layer that turns external events — GitHub, Slack, Discord, or manual API runs — into agent executions on registered Paseo daemons.

- **Trigger** = one named rule mapping a provider event (`on: slack.mention`, `github.issues`, `discord.mention`, `manual.run`) to an ordered workflow, gated by `filters` (hub `src/config/compiler.ts`, `AuthoredTriggerSchema`).
- **Step** = one agent execution: prompt, agent (`provider/model/mode/thinkingOptionId/options`), environment, `max_runtime`, `idle_timeout`, optional `output` schema and `allow_outputs`.
- **Environment** = named target: `kind: daemon` (+`daemon` slug, `cwd`, optional `worktree`), or `kind: fly` / `kind: docker`.
- **Project** = one active configuration revision plus the connections/daemons it uses. Config lives in `.paseo/hub.yml` (environments + agents) plus one trigger per `.paseo/workflows/<name>.yml`. A monolithic `triggers:` block in `hub.yml` is rejected (hub `src/config/bundle.ts`).
- **Connection** = per-organization provider integration: `slack_connections`, `discord_connections`, `github_connections` tables (hub `src/db/schema.ts`).

The daemon enrolls explicitly (`paseo hub connect`), persists `hub-relationship.json` under `PASEO_HOME`, and keeps an outbound WebSocket to Hub with only `hub.execution.*` authority (paseo `packages/server/src/server/hub/relationship-controller.ts`). The full transport/authority model is documented in the local [hub.md](../hub.md).

## How a Slack trigger runs

Verified in code:

1. **Inbound.** Slack event arrives via Socket Mode (hub `src/triggers/slack/source/`) or webhook POST to `/api/integrations/slack/events`. Transport is chosen by `SLACK_TRANSPORT=socket|webhook`. GitHub uses signed webhooks to `/webhook`.
2. **Normalize + persist** as a durable provider-event receipt; the dispatcher hands it to the durable workflow engine, which matches triggers against the project's active configuration revision.
3. **Match** (hub `src/triggers/slack/match.ts`): author must not be the bot, message must contain `<@bot>`, and must pass `filters` (`from_users`, `workspace`, `channels`, `connection`, `pattern`/`contains`). The prompt body is the message text after the mention.
4. **Dispatch.** Each step becomes one agent execution. The connected daemon receives `hub.execution.agent.create.request` with `executionId`, `cwd`, `prompt`, `mcpServers`, `providerOptions`, `toolPolicy`. The daemon creates a fresh workspace + agent; creates are idempotent on `executionId`.
5. **Agent → Hub.** The daemon's agent gets a Hub-injected MCP endpoint (`<hub>/agent-executions/<executionId>/mcp`) with a per-execution completion token. Tools: `finish_execution` (structured `output` if the step declares a schema) and the step's allowed output tools, e.g. `reply`.
6. **Reply to Slack.** `slack.reply` output → `chat.postMessage` into the triggering channel/thread (hub `src/triggers/slack/reply.ts`). Agent lifecycle states post reactions (eyes/hourglass/checkmark/x) back to the thread.
7. **Termination.** Hub sends `hub.execution.control.request` (`interrupt`/`archive`) with the durable execution ID.

All coordination is the outbound WebSocket RPCs plus the execution MCP endpoint. There is no shared file state; Hub stores everything server-side. Backend selection: `DATABASE_URL` set → Postgres (team/remote form); unset → embedded PGlite file DB (`src/db/runtime/internal/embedded.ts`), whose data directory `PASEO_HUB_DATA_DIR` overrides (default `$XDG_DATA_HOME/paseo-hub`, re-verified 2026-08-24 in `src/data-directory.ts`).

## Output and event surface (re-verified 2026-08-24)

- **Trigger events.** Slack: one event, `slack.mention`, fed only by the Slack `app_mention` callback — both transports subscribe to `bot_events: [app_mention]` (`slack-app-manifest.yml`, `slack-webhook-app-manifest.yml`), and normalization drops bot-authored and `bot_message` events (`src/triggers/slack/events.ts`). No DM events, no `message`, no slash commands. GitHub: `github.issues`, `github.issue_comment`, `github.pull_request_review`, `github.pull_request_review_comment`, `github.push` plus six semantic variants (`src/triggers/github/classification.ts`). Discord: `discord.mention`. Manual: `manual.run`.
- **Output capabilities.** The only registered capabilities are `slack.reply` and `discord.reply` (`src/providers/slack/index.ts`, `src/providers/discord/index.ts`) — both the same agent-invoked MCP `reply` tool (`src/execution-capabilities/outputs.ts`), each execution capped by the step's `allow_outputs` `max`. `allow_outputs.type` is a free-form `x.y` string at compile time (`EVENT_NAME` regex); a type only materializes into a tool when a capability is registered, so nothing else exists today (e.g. `manual.reply` appears in tests only). The agent chooses when to call it; nothing streams.
- **Timeline flow.** The agent timeline does flow daemon → Hub as `agent_stream` events carrying `timeline` items (`src/hub/protocol.ts`), but Hub uses them only to refresh the idle deadline and to acknowledge `finish_execution` tool calls (`src/daemons/lifecycle.ts`); nothing is forwarded to a channel. Same for `permission_requested`/`permission_resolved`: received, used for the idle deadline, never forwarded, and there is no respond RPC in the `hub.execution.*` protocol.

## Trigger configuration

### Slack trigger (verbatim, from `hub/examples/single-repo-team-bot/.paseo/workflows/slack.yml`)

```yaml
name: slack-mention
on: slack.mention
max_runtime: 2h
filters:
  from_users: [YOUR_SLACK_USER_ID]
steps:
  - id: classify
    environment: repository
    max_runtime: 2m
    idle_timeout: 30s
    auto_archive: true
    agent: classifier
    prompt:
      - include: partials/safety.md
      - include: partials/classifier.md
      - text: |
          <user-prompt>
          ${{ paseo.prompt }}
          </user-prompt>
    output:
      schema:
        type: object
        additionalProperties: false
        required: [kind, summary]
        properties:
          kind: { type: string, enum: [question, change, review] }
          summary: { type: string }
  - id: work
    environment: repository
    max_runtime: 90m
    idle_timeout: 10m
    auto_archive: true
    agent: worker
    github:
      connection: your-github-connection
      repositories: [your-org/your-repo]
      permissions:
        checks: read
        contents: write
        issues: write
        metadata: read
        pull_requests: write
      duration: 1h
    prompt:
      - include: partials/worker.md
      - text: |
          <context>${{ paseo.context }}</context>
          <user-prompt>${{ paseo.prompt }}</user-prompt>
    allow_outputs:
      - { type: slack.reply, max: 5 }
```

Required fields (verified, hub `src/config/compiler.ts`): `name`, `on`, `max_runtime`, and per step `id`, `environment`, `max_runtime`, `idle_timeout`, `agent`, `prompt`. For externally sourced events, `filters.from_users` must be non-empty — enforced at compile time (`validateTriggerLaunchSecurity`). Slack filters accept IDs only (user `U…`, team `T…`, channel `C…`).

### "Webhook triggers"

There is no generic user-configured webhook trigger type. Only GitHub and Slack have webhook transports:

- **GitHub**: App webhooks signed with `GITHUB_APP_WEBHOOK_SECRET`, URL `<PASEO_HUB_APP_URL>/webhook`. An unconfigured secret makes the endpoint return 503 for every delivery. Event triggers: `github.issues`, `github.issue_comment`, `github.pull_request_review`, `github.pull_request_review_comment`, `github.push`, plus semantic variants (`github.issue_created`, `github.pull_request_created`, …) (hub `src/triggers/github/classification.ts`).
- **Slack**: Events API to `/api/integrations/slack/events` with signing-secret verification; Socket Mode is the default alternative.
- **Discord** uses its gateway, no inbound webhook.

Trigger providers are exactly slack / discord / github / manual (verified: `src/triggers/*/provider.ts` `eventNames`).

## Follow-up behavior: no thread → session mapping

Every trigger event starts a new execution in a fresh workspace with a new agent session (verified: `paseo/docs/hub.md` "Every Hub execution creates a fresh Paseo workspace… The Hub cannot select or reuse an existing workspace"; `hub/src/workflows/engine.ts` creates one `executionId` per step per run with no key on `threadTs`). A follow-up mention in the same thread starts a brand-new agent with zero memory of the previous run.

The only continuity is ambient: a step that authors `${{ paseo.context }}` receives the _preceding_ thread messages as JSON prompt context (`materializeContext`, hub `src/triggers/slack/provider.ts`) — context is replayed as data, not as session state.

## Limitations (verified in code unless noted)

1. **No wildcard users.** `from_users` must be a non-empty explicit allowlist of IDs (or enriched usernames); a trigger without it is rejected at compile time. No `*`, no "all members of this channel." `channels` is likewise an explicit ID list.
2. **No thread → session mapping** for follow-up conversation (above).
3. **Account/connection caps per Hub instance:**
   - **GitHub**: one installation per instance — `github_connections.installation_id` has a global unique index (hub `src/db/schema.ts`). The FAQ claim of "no limit on how many you add" is contradicted by this index; the code limit wins.
   - **Slack**: one team per instance — `slack_connections.team_id` globally unique; the runtime provider configuration is a single row per provider, so one Slack app/app-token drives everything.
   - **Discord**: one guild per instance — `discord_connections.guild_id` globally unique.
   - Multiple _projects_ share connections, but within one instance the uniqueness caps apply.
4. **Authorization model is allowlist-only.** Org roles are just `admin`/`member` (+ `is_instance_operator` for entitlement overrides). There is no per-user "may create conversations" grant beyond the allowlist, and no per-user tool-approval authority: the protocol carries `permission_requested`/`permission_resolved` stream events, but Hub has no RPC or UI path to forward a tool-approval prompt to a channel. Unattended runs rely solely on pre-approved MCP tools + provider-native policy.
5. **Other limits relevant to a multi-user/multi-agent channel product:**
   - **Offline daemons**: dispatch fails, nothing is queued; the trigger gets a failure reaction + notice.
   - **Channel surface**: only `app_mention` in channels — no DMs, slash commands, or interactive components.
   - **No multi-agent conversation routing**: one trigger file = one ordered workflow; steps are sequential, not a shared agent pool the channel can address individually.
   - **Metering**: `executions.monthly` meter + `seats.max` cap enforced per execution creation.
   - **Prompt injection is out of scope** by design: "Hub does not sandbox the provider process or make external text safe" (hub `public-docs/hub/security.md`).
