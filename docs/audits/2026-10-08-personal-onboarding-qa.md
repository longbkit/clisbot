# Personal onboarding QA: Desktop, Hub, Tailscale and relay

Date: 2026-10-08. Commit under test: `1601af803`. Release builds of Desktop (macOS arm64), iOS
(simulator) and Android (arm64 emulator), driven use case by use case with the developer
confirming each step against [Device pairing](../features/access/device-pairing.md),
[Connect over Tailscale](../features/access/tailscale-connect.md) and the public docs.

## Use case 1: Desktop starts Clisbot, then Start Hub

| Step                              | Result                                                                                                                                                                            |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1.1 Open Desktop on an empty home | Matches the design: personal settings, `managedAccess.mode: off`, free loopback port, relay on, daemon started, no Hub, no Serve mapping.                                         |
| 1.2 Start Hub in the app          | Hub started and enrolled, success notice with **Set up a channel**. Tailscale fell back to relay because `:8443` was held by an unrecorded mapping (see D). Fixed findings below. |

## Public doc drift found, not yet changed

- `public-docs/index.md` says the CLI asks whether to enable relay. On a new home, `clisbot`
  tries Tailscale first and turns relay on as a fallback without asking.
- `public-docs/connectivity.md` says relay is off until enabled. Desktop and CLI onboarding
  turn it on for a new personal home.
- `public-docs/index.md` says **Pair Device**; the app and `connectivity.md` say **Pair a device**,
  and the Desktop home card says "Connect your phone to this daemon" instead of Host.
- The public docs have no path for Start Hub or channel setup from the app.
- `public-docs/hub/api.md` names `https://hub.paseo.sh` as the CLI's last-resort origin.

## Still open

- A Host whose saved profile still says managed access `off` after switching to `external`
  connects without a ticket and the daemon refuses with "Managed access ticket required"; the
  app shows a generic authentication error. Saying "Sign in to the Hub" needs a new refusal
  reason in `packages/client`.
- The suggested Connection name skips the channel's Connection names, not account ids; an
  account file with that id already in the configuration is left as it is when the Hub adds
  the Connection.
- macOS desktop releases fail: the repository has none of the Apple secrets
  `desktop-release.yml` reads (`APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_ID`,
  `APPLE_PASSWORD`, `APPLE_TEAM_ID`). With `CSC_LINK` empty, electron-builder stops with
  "packages/desktop not a file" (both macOS jobs of `v0.7.3-beta.1`, 2026-09-09).
- Browser check of `https://app.clisbot.com` pairing links (2026-10-08): Chrome 154 connects
  to a `ws://127.0.0.1` route; Safari blocks it. With relay in the link Safari falls back to
  relay and connects. Only `local` links (relay turned off, so `ws://127.0.0.1` alone) fail in
  Safari; the app now says so (`device-access/pairing-link-failure.ts`) instead of pointing at
  Tailscale and relay.
- `tailscale serve status` is read twice per start, and adopting a mapping on a new port
  leaves the old recorded authority unmanaged.
- `device-access/hub-settings.tsx` is over the 700-line limit (it was before this work).
- `src/clisbot/hub/settings/channel-identity-self-link.test.tsx` and
  `team-configuration-settings.test.tsx` fail to load (`Unexpected token 'typeof'`) on the
  unchanged tree as well.

## Environment notes

- Relay handshakes timed out on both daemon and Hub from 13:34 to 13:54 while a VPN client was
  reconnecting; they recovered on their own. Not a Clisbot fault.
- Each local desktop rebuild is a new ad-hoc signature, so macOS asks for the login keychain
  password for "Clisbot Safe Storage" again. Developer ID builds keep one Team ID and do not.
- Electron keeps saved Hosts and Hubs in `~/Library/Application Support/Clisbot` for every
  `CLISBOT_HOME`; switching homes in a test keeps the previous home's Hosts and Hub.
- Release iOS builds need `pod` on `PATH`; with CocoaPods installed as a gem under rbenv, the
  shims did not expose it until the version's `bin` was added.
