# Telegram vertical — deviation ledger

Differences from the OpenClaw source, each with its reason. The upstream
baseline, the per-file source mapping and the provenance deviations (`D-020`
and up, "this local file gathers these upstream files") live in
`upstream-sync.json`; this file carries the behavioral reasoning.

`D-019` was renumbered 2026-09-07 from a second `D-016` (duplicate id).

Slice 9 (2026-09-07) replaced the local outbound reimplementation with the
OpenClaw send/actions source. The boundary reasoning for that port is recorded
as `D-TG-010` … `D-TG-027` in `upstream-sync.json`; the entries below describe
the pre-port modules, several of which (`D-001`, `D-004`, `D-012`, `D-014`,
`D-017`, `D-021`, `D-030`, `D-031`, `D-032`) no longer have a live module and
are superseded by `D-TG-027`.

Slice 20 + 22 (2026-09-07) replaced the hand-rolled inbound transport with the
grammY 1.46.0 stack and ported the streaming/progress primitives. `transport/poll.ts`
and its test are deleted; the loop now runs through grammY `Api.getUpdates`
(`fusion/polling-session.ts`), the offset is upstream's own
`update-offset-store.ts` + `update-offset-persistence.ts` over the Hub keyed
store, and the vertical builds its `ChannelInboundEvent` from upstream's
`bot/body-helpers.ts` (`fusion/inbound-adapter.ts`). `D-007`, `D-011` and
`D-035` — the poll transport's simplified offset store, its local mention
normalizer and its provenance row — are retired with that file; the boundaries
that replace them are `D-TG-050` … `D-TG-055` in `upstream-sync.json`.
`D-TG-031` (the provider-observed thread binding) is CLOSED: `message-cache.ts`
is ported, `fusion/admission.ts` records every observed inbound message into it,
and `fusion/message-thread-observation.ts` answers from that cache instead of
denying unconditionally.

Slice 9b (2026-09-07) restored the action runner (`action-runtime.ts`,
`handleAction`, the presentation → inline-keyboard builders and the three
callback-data encoders). `D-TG-012` and `D-TG-022` — the slice-9 omissions of
those builders and of `handleAction` — are retired; the boundaries that
remain are `D-TG-029` (credentials), `D-TG-030` (sticker vision),
`D-TG-031` (provider-observed thread binding) and `D-TG-032` (the one dropped
test case), all in `upstream-sync.json`.

- **D-001 — write-backs target the keyed-store seam, not the OpenClaw config file.** The pinned `sent-message-cache` / `resolveAndPersistChatId` persist to OpenClaw-owned config; the in-repo L1 points `recordSentMessage` and the chat-id persistence at the plane's keyed-store seam (`telegram.sent-messages`, `telegram.update-offsets`, `telegram.bot-info-cache` namespaces via `openTelegramSeamStores`). Blueprint §7 decision 3a: ships with the pull; the pglite backing swap is a separate Hub-side commit (channel code identical on either backing).
- **D-002 — retry-after cap decided at 60 s** (`TELEGRAM_OUTBOUND_RETRY_AFTER_CAP_MS`). The pinned retry-after boundary caps the 429 `retry_after`; the exact pinned constant was not in the listed reference files, so it is decided here. Bounded retries: max 3 retries, 3 s default backoff.
- **D-003 — rich-HTML ON by default; plain text on the account's explicit `richMessages: false` opt-out.** (Amended 2026-08-29 — supersedes the original off-by-default entry: live users saw raw markdown leaking — literal `**`, backticks, `[x](url)` — because the vertical defaulted to plain text while the pinned OpenClaw funnel always renders markdown.) The in-repo vertical now matches the pinned behavior: `sendTelegramText` converts the text markdown → Bot API HTML through `format.ts` (upstream source at `5d8067a4483`: `markdownToTelegramHtml` + `splitTelegramHtmlChunks`) and posts every chunk with `parse_mode: HTML` UNLESS `channels.telegram.accounts.<id>.richMessages` (or the channel-level default it inherits) is explicitly `false`. The key was read off a nested `config` sub-object until `D-TG-056` unified the vertical's two account readers on upstream's flat entry. The rich path keeps the legacy 4000-char chunk limit (OpenClaw `send-message-text.ts`: the HTML path is non-rich-blocks, so `maxChars = 4000`), not the 32 768 rich-blocks limit. The `richMessages` account config key is an in-repo decision (the pinned funnel has no such account opt-in — it always renders markdown); here it is an OPT-OUT, not an opt-in. Fusion turns the NATIVE rich-blocks path (`send-message.ts` `richMessages === true` → `sendRichMessage`) on by default too, and it does that in the Hub, not here: `packages/hub/src/channels/config/compile-support.ts` `ACCOUNT_CONFIG_DEFAULTS` fills an absent `richMessages` with `true` when it compiles a Telegram account. The vertical's read stays byte-identical to upstream, and an authored `false` still wins. Live proof: `docs/tests/channels/p0-live-scenarios.md` wave 5b (message 173, forwarded as 174, a `rich_message` with heading/list/blockquote/pre/table blocks).
- **D-004 — surface narrowed to text send + native media + chat-id resolution + poll.** The pinned chunk's poll/sticker/inline-keyboard/location/reaction surface, the prompt-context projection, and the ingress spool/worker/liveness machinery (`polling-session.ts`'s non-poll half) are not ported: the native ingress worker is excluded by `docs/audits/pinned-vertical-contracts/telegram-monitor.md`. The outbound surface is `sendText` (text-only, P0) plus `sendMedia` (one local media file through a mime-routed Bot API method — the G7–G11 addition, D-014).
- **D-005 — grammy stack loads lazily, not at module load.** The pinned chunk is a compiled dist with the stack inlined; the in-repo ESM dist instead defers `import("grammy")` to `createTelegramApi`'s default factory and defers `apiThrottler` to `createTelegramAccountThrottler`. Reason: the L2 poll loop and the shared-L3 inbound path must stay grammy-free (and unit-testable without the dep), and a sync `require` is invalid in the ESM dist (coordinator pre-flight fix). `@grammyjs/runner`'s `sequentialize` is no longer referenced (its pinned-dep slot was the B1 boundary; the in-repo loop is single-threaded per account by construction) — the dep stays pinned per blueprint §7 decision 2.
- **D-006 — `to` target grammar decided.** `<chatId>` or `@username`, optional `:topic:<id>` suffix parsed by `parseTelegramTarget`; `threadId` on the `SendTextArgs` is a fallback numeric topic when `to` carries none. The pinned `targets.ts` grammar was not among the listed reference files, so the suffix form is decided here (matches the Hub's `:topic:` convention).
- **D-007 — offset store simplified.** One key per account store root (`"telegram"`); the pinned `version` field and the legacy v1/v2 parse ladder are dropped (in-repo store, no legacy migration path). Rotation drop semantics kept: the offset is ignored when the bot-id prefix or the token fingerprint no longer match.
- **D-008 — cache timestamp is epoch ms, not an ISO string.** The pinned `bot-info-cache.ts` persists `fetchedAt` as an ISO string; the seam store is JSON-native and the shared `HostKeyedStore` has no date semantics, so `TelegramBotInfoCacheState.fetchedAt` is a number. TTL 24 h unchanged.
- **D-009 — bot-info shape narrowed.** `TelegramBotInfo` keeps `id / is_bot / first_name / username` (the L1's pre-existing shape); the pinned `normalizeTelegramBotInfo`'s full capability booleans are not ported — nothing in the drive surface reads them. `probeTelegramBotInfo` passes grammy's `getMe` result through; the cache re-validates on read via fingerprint + TTL instead.
- **D-010 — duplicate-token guard is a config scan, not a drive-time probe.** start-account.md pins the native guard to `findTelegramTokenOwnerAccountId` (scan + throw). `assertNoDuplicateTelegramTokens` scans `cfg.channels.telegram.accounts.*` for equal non-blank `botToken`s and throws before the probe — same observable behavior (a stray second entry fails the account at drive time), no network in the guard.
- **D-011 — mention facts only, no mention policy.** `normalizeTelegramInboundEvent` computes `wasMentioned` (entity-mention of the bot, `@username` span, or a `/command` line) as a FACT; the policy (route matching + `fallback`) is the Hub plane's, per the shared L3 contract. The pinned `bot-handlers.*` / `bot-message-dispatch.*` trees are out of scope by design.
- **D-012 — `getChat` lookup only, no chat-id persistence cache.** `resolveChatId` does numeric pass-through or a live `getChat` lookup per send; the pinned `resolveAndPersistChatId`'s persist half would have written resolved ids to the config file — replaced by the seam write-back of the delivered message itself (D-001), which is what read-back matching needs.
- **D-013 — native approval-card seam: `reply_markup` on chunk 0 + `editMessageText` update + `callback_query` wired in poll.** The P0 slice (2026-08-27, COMPAT(clisbot-control-plane)) adds `replyMarkup` / `cardPosted` to `sendTelegramText` (the keyboard rides chunk 0 next to the thread params — the Bot API's single-reply-target rule) and `editTelegramMessageText` for the card's in-place update (`clearCard` strips the keyboard via `reply_markup: { inline_keyboard: [] }`; the 400 "message is not modified" is treated as success). The bot-side half (2026-08-28, E2) is now wired: `transport/poll.ts` parses `callback_query` the way the Slack vertical parses `block_actions` — `from.id` → `telegram:<id>`, `message.chat.id` / `message.message_id` / `message_thread_id` → location, the opaque `callback_data` handed verbatim to the same channel-agnostic `channelRuntime.approvalAction` seam (hub-side needs no change); reply via a SILENT `answerCallbackQuery` (no text/alert — the hub-side card update is the user-visible outcome), ack-first (the ack fires before the handoff, so a faulty callback cannot wedge the poll, and the transport's `update_id` seen-set + the hub's exactly-once latch make a stale/second tap inert). Root-kind normalization: `private` → `dm`, everything else → `group` (the plane has no Telegram "channel" kind). One wire change from the pinned fetch-only monitor: `allowed_updates` is now SENT on the `getUpdates` URL with `callback_query` added to the list (the pinned monitor omitted the param, so Bot API served the FULL update set — the poll advanced past the unused types, including unhandled `callback_query` updates; the explicit list pins the served set to the vertical's declared surface and is what makes the callback surface part of the pinned contract).
- **D-014 — native media outbound (`plugin.outbound.sendMedia`, G7–G11).** The 2026-08-28 wave-3 addition ports the one-file media post so the Hub can deliver an agent-produced local media file. `sendMedia` (one call = one file = one Bot API call) routes the file's mime (from its extension, `mimeFromExtension` in the shared `media-policy.ts`) to a Bot API method: `image/gif` → `sendAnimation`, other `image/*` → `sendPhoto`, `video/*` → `sendVideo`, `audio/ogg`/`audio/opus` → `sendVoice`, other `audio/*` → `sendAudio`, else → `sendDocument` (mirror of OpenClaw `extensions/telegram/src/outbound-media.ts` `resolveTelegramOutboundMediaSenders` + `packages/media-core` mime-kind mapping; the photo→document fallback on oversized-photo and the `forceDocument`/`asVoice`/`sendImageAsPhoto` toggles are NOT ported — the drive path posts one file with no retry-as-document ladder). The mime→method table is a pure function (`telegramMediaMethod` in `outbound-media.ts`), unit-tested against the OpenClaw routing. The 50 MB Bot API upload cap (`TELEGRAM_MAX_MEDIA_BYTES`) lives in the shared `media-policy.ts` (ONE home, shared with the Slack vertical's 250 MB cap); the G11 gate runs BEFORE the send and is SIZE-ONLY (amended 2026-08-29: the Bot API's `sendDocument` accepts any file type up to the cap, so an unknown/unmapped extension posts as `application/octet-stream` rather than being refused — only an oversized file is not dropped, and its in-channel notice ("Could not post media <name>: too large (Telegram limit 50 MB)") is posted through the plain `sendText` path with `mediaPosted` reporting false), while a transport fault (missing local file, Bot API failure) throws so the Hub's `failDelivery` owns it. `message_thread_id` (topic targeting) rides the media request via the shared `buildTelegramThreadParams`, and the delivered message is written back to the seam store (D-001) exactly as `sendText` does.
- **D-015 — the injected Bot API fetch normalizes Node `Readable` bodies to web `ReadableStream`s (the multipart-upload fix).** The L1 always hands grammy its own fetch (the plane's undici `globalThis.fetch`, wrapped for the per-request timeout in `createTelegramClientFetch`), never grammy's default Node fetch (node-fetch). grammy's `createFormDataPayload` builds every file-upload body as a Node `Readable` (`stream.Readable.from`), which node-fetch transmits fine but undici's `fetch` cannot — it wants a web `ReadableStream`/Blob/Buffer/string, so every multipart upload threw `HttpError "Network request … failed!"` while JSON calls (string bodies) succeeded. `normalizeFetchInit` (in `leaves/telegram-policy.ts`) detects a `Readable` body, converts it with `Readable.toWeb`, and sets `duplex: "half"` (undici requires it for streaming bodies); non-`Readable` bodies pass through unchanged. This runs in BOTH the timeout and no-timeout branches, because the defect is the injected-fetch substitution itself, not the timeout. Found live 2026-08-28 (wave-3 sweep, G7–G11 media outbound FAIL → the isolation matrix proved any injected fetch breaks uploads, even identity passthrough). No pinned counterpart: the pinned monitor is "direct fetch, no grammy", so this whole grammy-fetch boundary is already in-repo-only.
- **D-016 — omitted `timeoutSeconds` defaults to 30 seconds for Bot API requests.** The per-account throttler serializes group sends; an unbounded first fetch therefore blocks every later assistant/progress post for the chat. An explicit account timeout keeps its configured value. This is a host-safety default at the already in-repo-only injected-fetch boundary, not persisted compatibility config.
- **D-019 — multi-chunk topic sends carry `message_thread_id` (and silent) on EVERY chunk, not just chunk 0.** The pull-era `buildChunkParams` dropped `message_thread_id` on chunk 1+ (a misreading of the pinned "single-use reply semantics" — that applies to the reply-to QUOTE, not to topic placement), so a long reply into a forum topic scattered its continuation chunks into General. Pinned `send-message-text.ts` keeps the thread id + `disable_notification` on every chunk (`buildThreadParams` is unconditional per chunk; only the reply-to is gated on `shouldIncludeReply`). Fixed 2026-08-28 (wave-3, live G10 re-drive): `buildTelegramThreadParams` now builds ONLY the per-chunk params (`message_thread_id` + silent) and a new `buildTelegramReplyParams` builds the chunk-0-only `reply_parameters`; the card's `reply_markup` merges into that same chunk-0-only object (the Bot API's one-reply-target rule is unchanged); `buildChunkParams` merges the thread params onto every chunk. The media post carries both (one media message = the text path's chunk 0). Live evidence of the defect: G10 re-drive — essay reply into topic-1 posted chunk 0 at `message_thread_id=2`, continuation chunks at `thread=null` (General). (Supersedes the F-07 register's "chunk 0 only" wording — see the amendment there.)
- **D-017 — retired reply-text media parsing.** The pinned OpenClaw vertical parses reply text for media paths through its `reply-media-paths` runtime. The in-repo vertical retires that behavior: media is posted only through the Hub's `message` MCP tool media params (`attachments`/`media`/`buffer`), routed into this vertical's `outbound.sendMedia`. `sendText` remains text-only; G7–G11 semantics remain on `sendMedia`.
- **D-018 — `plugin.outbound.typing` (the `sync.progress.typingIndicator` surface).** The pinned vertical raises the cue inside its own ingress spool (`telegram-ingress-spool-Dd3cDhXe.js:5351-5363`: `sendChatAction(chatId, "typing", buildTypingThreadParams(replyThreadId))`, plus a `record_voice` cue for audio answers); the in-repo vertical has no spool (D-004, and the native ingress worker is excluded by `telegram-monitor.md`), so the drive surface owns the cue and the HUB decides when the turn starts and ends: `outbound.typing({cfg, accountId, to, action, indicator, threadId})` sends `sendChatAction("typing")` on `start` and nothing on `stop` (the action lapses in ~5 s, so a clear call would be a call for nothing). The refresh that replaces the spool's loop lives HERE, not hub-side: `TELEGRAM_TYPING_REFRESH_MS` (4.5 s, inside the vendor's ~5 s expiry) re-sends until `stop` cancels the timer, because the expiry is Telegram's and a Hub-wide heartbeat would guess one cadence for wires that do not share it. Two pinned facts are kept deliberately: `message_thread_id` rides the typing action INCLUDING the forum's General topic (`1`) — the opposite of a send, where the Bot API rejects `thread_id=1` (`sent-message-cache-BGcQC26h.js:1784-1790`, "Empirically, General topic (id=1) needs message_thread_id for typing to appear") — and the pinned `record_voice` audio cue is NOT ported (no voice-answer path at P0). The pinned breaker (`TELEGRAM_MAX_CONSECUTIVE_TYPING_FAILURES = 5`) is replaced by the Hub's release-on-fault: a drive that throws drops the lease and logs once, and this file cancels its own timer on a failed tick. No reaction surface exists on the Bot API, so `messageReaction` is answered here as "nothing to do". Contract: `docs/audits/pinned-vertical-contracts/typing.md`.
